## Контекст

Мотивация и границы описаны в [proposal.ru.md](proposal.ru.md). В исходном плане карточка представляла один принятый Work. Теперь продукту нужна задача, которая существует до выполнения, переживает изменения требований и объединяет оценку, реализацию и последующие запуски. Это намеренно заменяет прежнее решение в плане, но не меняет контракты неизменяемого выполнения Factory.

Текущие ограничения:

- `WorkEnvelope` и принятые версии Factory Configuration/Flow неизменяемы. Хранилище приёма и миграция `0047_dark_factory_authority.sql` обеспечивают повтор Work в пределах его области идемпотентности и один Factory Run на Work.
- `add-github-work-source` уже отделяет наблюдение и приём Source от эффектов Reporter, использует стабильные нативные идентификаторы и сохраняет восстанавливаемую отчётность. Его идентичность Work, ограниченная входом, намеренно различается у независимо настроенных pipeline.
- Прямая публикация текста запланирована в `add-factory-bugfix-quickstart`; существующий приём Artifact сохраняется. У входных Artifact, принадлежащих Project, нет вымышленного происхождения от Build.
- Существующие диагностика, логи Build, проверка допустимости команд управления Factory, точные свидетельства и предусловия Run пригодны для повторного использования. AI-профили и зарегистрированные рабочие Agent — разные понятия; управление профилями ролей остаётся отдельным change.

## Цели и то, что не входит в задачу

**Цели:**

- Дать ручным и импортированным задачам постоянное внутреннее место, независимое от провайдера и цели выполнения.
- Сохранить точную связь требований с выполнением при нескольких pipeline и изменениях требований.
- Сделать видимыми владение синхронизацией и конфликты, не позволяя внешним изменениям управлять уже идущим выполнением.
- Позволить каждому Project настраивать бизнес-статусы и разрешённые переходы с явными действиями pipeline и отдельным маппингом провайдера, без вывода жизненного цикла из завершения Run или меток.
- Повторно использовать существующие выполнение, отчётность, публикацию входов, защищённое управление и пагинацию, не вводя параллельные реализации.

**Не входит в задачу:**

- Замена планировщика Factory, изменяемый Work Envelope или несколько Run для одного Work.
- Полное соответствие возможностям платформ разработки, произвольное двустороннее слияние документов, создание внешних тикетов, зеркалирование между провайдерами, синхронизация комментариев и вложений или новые нативные адаптеры GitLab/Jira.
- Чат с агентами, запуск по упоминанию, автоматическое делегирование, аутентифицированные персональные назначения и входящие очереди или новый дизайнер pipeline.
- Второй планировщик выполнения, произвольные скрипты и условия workflow, автоматически вычисляемые цепочки переходов или автоматическая и массовая миграция существующих Issue на новые workflow.

## Решения

### 1. Issue владеет редактируемым замыслом; Work — одним зафиксированным выполнением

До обновления общего глоссария при реализации используется следующая терминология этого change:

| Термин | Значение |
| --- | --- |
| Issue | Постоянная задача Project со стабильным внутренним ID и отображаемым ключом внутри Project |
| Редакция Issue | Неизменяемая версия названия, описания, входных критериев приёмки и ограниченных бизнес-метаданных задачи |
| Workflow Issue | Принадлежащие Project неизменяемый набор бизнес-статусов и конечная политика разрешённых переходов; независимы от Factory Flow |
| Переход статуса Issue | Одно разрешённое организационное перемещение с точными workflow, статусами до и после, данными конкурентного доступа и происхождением от actor, действия или наблюдения |
| Запрос выполнения Issue | Явный сохраняемый запрос, связывающий редакцию Issue с точной целью Factory и обычным приёмом |
| Work Envelope | Существующий неизменяемый принятый вход выполнения; по-прежнему владеет ровно одним Factory Run |
| Связь с внешним источником | Необязательная связь с одной внешней нативной задачей, доступной по правам, и версионируемой политикой синхронизации |

У Issue может быть от нуля до многих запросов выполнения и связанных Work Envelope. Каждый Work принадлежит не более чем одному Issue в своём Project; повторные попытки, вложенные Flow и циклы требований остаются дочерними объектами исходного Run. Существующий Work без Issue остаётся действительным и доступным через прежние представления до дозаполнения связей.

Для создания Issue нужны видимый Project и соблюдение ограничений названия и описания, включая правила непустого текста. Репозиторий, документ приёмки, установленный провайдер, модель и Factory Configuration не требуются. В черновике критерии приёмки могут быть неполными. Сервер проверяет настроенные конечные значения бизнес-метаданных и объявленные ограничения. Статус в метаданных отражает организацию задачи; он не может установить принятый Decision, завершить Run или дать полномочия на доставку. Изменение профиля и приоритета Issue влияет только на последующие проверенные запросы, но не на намерение планирования, уже зафиксированное в Work/Build.

Используется небольшой агрегат Issue с указателем на текущую редакцию, редакциями только на добавление и точными связями с выполнениями и источником. Не создаётся универсальная платформа event sourcing или вторая копия изменяемого состояния выполнения Factory. Конкурентное редактирование требует наблюдаемой версии Issue; точный повтор команды в её области идемпотентности возвращает исходную редакцию, не перечитывая новую вершину истории. Прогресс выполнения не должен менять редактируемую версию Issue только ради обновления индикатора.

Рассмотренная альтернатива: сделать Work редактируемым или создавать отдельную карточку для каждого pipeline. Первое нарушает неизменяемость входов, второе лишает пользователя постоянной задачи. Отдельная идентичность задачи над существующим выполнением обоснована изменившимися требованиями.

### 1a. Workflow Project определяют статусы; переходами владеет одна команда

Публикуются ограниченные неизменяемые версии workflow Project со стабильными ID workflow, статусов и переходов, отображаемыми названиями и порядком, полями `initial_status_id` и `terminal_status_ids` на уровне workflow и явными рёбрами from/to с разрешёнными источниками команд и правами. Запись статуса содержит только стабильный ID и отображаемое название; порядок в векторе определяет порядок показа. Workflow содержит одну обязательную ссылку на начальный статус и ограниченный уникальный набор ссылок на завершающие статусы, который может быть пустым. Все ссылки принадлежат собственному списку статусов workflow. Отсутствующие или неизвестные начальные ссылки, неизвестные, повторяющиеся и превышающие лимит завершающие ссылки, а также поля `initial`/`terminal` у отдельных статусов отклоняются. Источник истины один; флаги и парсер совместимости не добавляются. Ссылки рёбер, уникальность и границы проверяются как прежде. Повторное открытие может быть явно разрешённым ребром; путь и промежуточные перемещения не выводятся автоматически. Необязательное конечное условие может требовать точного текущего свидетельства принятого выполнения через существующие контракты допустимости; скрипты, переключение по имени фазы и второй интерпретатор Flow не вводятся. Организационный завершающий статус никогда не создаёт Decision, не завершает Run и не разрешает доставку.

Выбор начального и завершающих статусов хранится в неизменяемом определении workflow, а не во второй изменяемой записи настроек. Его изменение публикует следующую версию workflow через существующую границу предусловий и повторов. У задачи 2.1 пока нет выпущенной HTTP-схемы или данных workflow в PostgreSQL, поэтому промежуточная форма с флагами заменяется напрямую. Сохраняются те же стабильные ID, выборы по умолчанию и значения переходов, без парсера прежнего формата.

У каждого Project с Issue есть корректный редактируемый workflow по умолчанию из обычных декларативных данных шаблона; первый создатель задачи не обязан администрировать workflow. Ручное и импортированное создание начинается с начального статуса этой версии. Названия шаблона New, Triage, Ready, In progress, Review, Done и Declined — примеры, а не перечисления домена. Каждый Issue закрепляет свою версию workflow; новый вариант по умолчанию применяется только к новым Issue. Версии и идентичности статусов, на которые есть ссылки, сохраняются доступными. Переход существующего Issue на другую версию требует отдельных проверенных полномочий, его текущей версии и статуса, явного корректного соответствия статусов, совместимого маппинга источника и текущего владения полем статуса. Он не меняет зафиксированное выполнение, не отправляет неявные эффекты провайдеру и делает прежнюю применимость автоматических переходов недействительной. Массовая миграция не входит в задачу.

Ручные перемещения, принятые действия pipeline и сопоставленные наблюдения полей под управлением источника вызывают одну узкую команду и границу хранилища переходов. Она проверяет конкурентные изменения Issue и статуса, точное ребро workflow, происхождение и права, применимые свидетельства и владение полем. Атомарно публикуются итоговая редакция, история статуса, квитанция повтора, аудит и любое разрешённое сохраняемое намерение исходящего изменения. Обычные обновления редактируемых полей не могут напрямую задавать статус или workflow. Отклонённые, устаревшие и запрещённые перемещения не публикуют частичный статус или намерение изменения у провайдера. Точный повтор возвращает исходный результат после последующих перемещений, а не применяет ребро снова. История записывает ID до и после, версию workflow, безопасную причину и actor либо точное выполнение, действие или наблюдение источника; обычное обновление прогресса не создаёт редакций статуса.

Пример конфигурации, независимо редактируемой для каждого Project:

| Явный триггер или действие | Бизнес-переход |
| --- | --- |
| Ручное создание или импорт | Начальный статус New; без выполнения |
| Принятое настроенное действие входа в Triage | New -> Triage |
| Принятый исход Triage «подходит / классифицировано» | Triage -> Ready |
| Принятый исход «дубликат / вне целей проекта» | Triage -> Declined с причиной |
| Принятые действия входа в реализацию и review | Ready -> In progress -> Review как отдельные объявленные перемещения |
| Принятое настроенное действие завершения с требуемыми свидетельствами | Review -> Done |

Если действие не настроено, завершение Triage или любого Run не меняет статус Issue. Ручное перемещение статуса не запускает pipeline и не отменяет текущее выполнение. Существующие независимо включённые входы Source сохраняют собственную семантику приёма; бизнес-статус не является запросом выполнения.

### 1b. Действия статуса в pipeline явные и привязаны к применимости

Для установленной команды изменения статуса Issue используется существующая общая граница публикации и выполнения доверенных действий. Оператор выбирает объявленный исход этапа, точные Project, workflow, версию и переход с разрешёнными требованиями к свидетельствам. На вход поступают типизированные принятые данные; сырой текст модели или необработанный сбой не могут выбирать ребро. Для локального действия Issue не нужны внешний источник, Reporter, токен или специальный тип узла. Если связанного Issue нет, его нельзя угадывать или создавать: известная несовместимая конфигурация отклоняется до выполнения, либо показывается явный безопасный результат недоступности действия. Существующие несвязанные Work и обычное поведение Flow сохраняются.

Разрешённая связь выполнения с Issue сохраняет происхождение содержимого и редакции требований, а также ожидаемый маркер применимости статуса. Только успешные переходы статуса из сохранённой цепочки команд того же выполнения могут продвигать маркер для его следующего настроенного действия; изменение только статуса не должно ошибочно делать неизменённые требования недействительными. Зафиксированное ручное перемещение или перемещение от источника, переход из другого выполнения, принятие другой версии workflow и изменение требований делают прежнюю применимость недействительной, даже если отображаемый статус или текст требований позже вернутся к прежнему значению. Сам по себе запуск другого выполнения, наблюдение неизменённых данных или изменение посторонних метаданных применимость не отменяют. При принятии действия повторно проверяются эта привязка, текущее предусловие Issue и статуса, точное ребро, текущие права и свидетельства. Конкурирующие Run не могут использовать правило «побеждает завершившийся последним». Устаревшее или конфликтующее перемещение сохраняет исходный результат и историю принятого выполнения, не запускает новое выполнение и не пересчитывается молча относительно новой вершины. Для согласования нужна новая проверенная команда с текущими полномочиями. Повтор уже зафиксированной команды статуса остаётся действительным после последующих изменений.

Точная команда и исходная идентичность действия сохраняются и возобновляются существующим механизмом сохраняемых намерений и повторов. Прерывание между принятием действия и применением статуса не может дублировать историю или потерять зафиксированное перемещение. Маркер и квитанции — ограниченные метаданные применимости, а не второе состояние Run или движок владения. Успех действия статуса никогда не заменяет обязательную контрольную точку выполнения. Существующие зафиксированный Work и команды управления его Run остаются источником полномочий на выполнение.

### 2. Явные запросы выполнения фиксируют входы через существующий приём

Начало работы отделено от сохранения задачи. Проверяются точная редакция Issue, видимые версии Factory Configuration и Repository, ограниченный маппинг текста задачи и приёмки, политика базовой ссылки и требуемые возможности. Отсутствующий вход приёмки — понятная исправимая ошибка валидации; он не генерируется из пустого поля. Устаревшая проверенная версия Issue вызывает конфликт; сервер не должен молча подставлять последнее описание.

Запрос выполнения, дайджесты редакции и содержимого, выбранная цель и идентичность повтора сохраняются до возобновляемой публикации входов. Повторно используются одна служба публикации входов Project и существующая проверка приёма. Восстановление проходит через этапы намерения, доверенной фиксации исходного кода, публикации неизменяемого входа, приёма и связывания с точными сохранёнными идентификаторами. Точный исходный код фиксируется один раз до публикации байтов под текущим защитным маркером сохранённой операции и повторно используется для обычного приёма; изменяемая ссылка не разрешается снова. Повтор приёма по-прежнему проверяется до поиска изменяемого исходного кода. Повтор после потерянного подтверждения возвращает тот же Work/Run; запрос не считается принятым, пока связь не сохранена надёжно. По возможности используется атомарная операция хранилища; для уже зафиксированного приёма — сохраняемый шаг согласования. Нельзя компенсировать сбой удалением Work или приёмом замены.

Намеренное последующее выполнение получает новый идентификатор запроса выполнения и новую обычную ручную идентичность Work в своей области. Оно не переиспользует транспортный ключ идемпотентности и не выдаёт себя за повтор предыдущего Run. Существующий автоматический приём Source сохраняет текущую идентичность дедупликации в пределах входа; принятый Work идемпотентно связывается с каноническим Issue без изменения ключей повтора. Одно внешнее изменение само по себе не является запросом выполнения. Существующие независимо настроенные предикаты последующих входов по-прежнему могут разрешать отдельный обычный приём.

Снимок выполнения включает точную редакцию, идентичности входов задачи и приёмки, наблюдение источника при наличии, конфигурацию, репозиторий и базовую ревизию, а также версии маппинга. Эффекты источника дополнительно привязывают разрешённую связь с источником, нативную цель и маппинг отчётности к исходной границе выполнения или действия. Связь с карточкой не даёт права при отправке выбирать другой текущий источник. Позднее подключение источника не может задним числом включить автоматическую отчётность для несвязанного выполнения. При изменении требований UI помечает идущий запуск как использующий более раннюю редакцию. Повторные попытки используют тот же снимок; запуск по изменённым требованиям — отдельный проверенный запрос. Несколько активных выполнений возможны только по существующим правилам WIP, прав и бюджета. Карточка перечисляет их все, а не выбирает вымышленного единственного текущего агента.

Рассмотренная альтернатива: читать изменяемое тело Issue при каждом вызове модели. Отклонена, поскольку повторные попытки и результаты перестали бы описывать исходно принятую задачу.

### 3. Каноническая внешняя идентичность независима от идентичности приёма pipeline

На первом этапе у каждого Issue ноль или одна основная связь с источником. Связь уникальна в своём Project и принятом разделе безопасности по доверенному пространству установки провайдера, нативной идентичности ресурса и нативной идентичности элемента. Отображаемый номер, название, URL, credentials, отображаемое имя подключения и ID входа pipeline не являются этим ключом. Совместимая ротация или смена принятого подключения сохраняет установленную нативную идентичность. Задачи нельзя группировать между Project или считать одинаковыми по тексту.

Конфигурация импорта и синхронизации отделяется от автоматического приёма pipeline. Разрешённый Source может создать или обновить связанный Issue без настроенной цели выполнения. Если настроенный вход также принимает Work, он связывается с этим Issue по тому же нативному ключу. Два входа, наблюдающие один внешний тикет, получают один Issue и две независимо дедуплицируемые связи Work. Изменённые описание, метки, токен или версия входа не создают новый Issue.

Поддерживается явное связывание видимого несвязанного ручного Issue с существующей внешней задачей после проверки чтения в разрешённой области и проверки владения полями. Если нативная задача уже принадлежит другому Issue этого Project, возвращаются безопасный конфликт и каноническая видимая ссылка; истории задач не сливаются молча. В исходные границы не входят замена источника, зеркалирование нескольких источников или автоматическое создание удалённого тикета. Связи с другим Project и скрытые связи не раскрываются.

Повторно используются установленные операции Source и ограниченный механизм наблюдений и прогресса. Синхронизация должна обновлять сохранённые связи, даже когда тикет перестал соответствовать селектору выполнения. Разрешённая связь может иметь собственную политику входящего обновления при отключённом входе выполнения. Отключение подключения, отзыв его разрешений или выключение синхронизации связи прекращает соответствующий доступ к провайдеру. По возможности наблюдения разделяются с механизмом приёма; отдельный несвязанный poller провайдера, хранилище credentials или маршрутизатор по меткам не создаются.

### 4. Владение полями ограничивает синхронизацию

Каждая связь закрепляет проверенную неизменяемую версию маппинга и показывает независимые настройки pull и push. У каждого управляемого поля один владелец и направление: входящие изменения под управлением источника, исходящие изменения под управлением OctaCity либо отсутствие синхронизации. Сначала импортируются название и описание из источника, а наружу проецируются настроенные принятые бизнес-исходы. Другие поля требуют явно объявленной возможности чтения или записи и ограниченного маппинга. Поля под управлением источника в связанной карточке явно доступны только для чтения; остальные остаются локально редактируемыми. Локальная задача не зависит от провайдера.

Маппинг внешних статусов отделён от workflow Project и выбора действий Flow. Он ссылается на стабильные внутренние ID статусов и применимую версию workflow, затем сопоставляет либо принятый статус под управлением OctaCity с точными поддерживаемыми нативными значениями и эффектами, либо свежие нативные наблюдения под управлением источника с одним настроенным разрешённым внутренним переходом. Нативные состояния open/closed и названия меток не имеют встроенной эквивалентности Done, Ready или приёмке. Правила pull должны давать ровно одну цель либо оставаться явно несопоставленными или неоднозначными. Нельзя выбирать по порядку правил, придумывать промежуточные переходы или обходить ребро и требования свидетельств. Импортированная задача начинается с начального статуса workflow; несовместимый последующий статус источника остаётся явным состоянием синхронизации, а не проталкивает карточку через запрещённый переход.

Статус под управлением источника запрещает ручную замену и замену действиями pipeline. Для статуса под управлением OctaCity нативное расхождение — свидетельство для отчётности или конфликта, а не входящая команда статуса. Несинхронизируемый статус остаётся локально управляемым. Смена владельца — проверенная команда маппинга, а не запасной путь после отказа в переходе. Принятие другой версии workflow и замена маппинга проверяют все статусы и поддерживаемые эффекты, на которые есть ссылки, и никогда не перенаправляют принятую операцию. GitHub может проецировать управляемые метки и необязательное open/close через существующую возможность. Нативный переход другого провайдера предлагается только при реальной поддержке. Несколько нативных совпадений, неподдерживаемые эффекты и недостающие разрешения — явные ошибки или состояния. Эхо входящего обновления не создаёт новый переход, редакцию, действие или Run.

Одно нативное управляемое поле для одного исхода нельзя одновременно менять исходящим обновлением статуса карточки и прямым действием Factory по обновлению источника. При публикации Flow и маппинга и при принятии действия перекрывающиеся производители отклоняются либо выбирается один явно проверенный производитель через существующий механизм полномочий на эффекты. Одна лишь последующая связь не добавляет вторую запись. Оба производителя используют существующие порядок и восстановление Reporter, а не отдельный outbox.

Наблюдения pull — данные, а не команды. До создания редакции Issue проверяются область источника, нативная идентичность, ограничения содержимого и происхождение. Повторное или неизменённое наблюдение не создаёт новую редакцию содержимого. Сохраняются свидетельства порядка и квитанции наблюдений, чтобы старая страница не могла перезаписать более новую принятую редакцию. Если у провайдера нет надёжных сравнимых версий, используются повторное наблюдение и согласование по существующему ограниченному контракту провайдера. Неопределённость показывается явно, а не разрешается порядком прибытия. Pull никогда не переписывает снимок выполнения, не отменяет и не перезапускает работу автоматически и не даёт полномочий на жизненный цикл из нативных меток или состояния.

Намерение push возникает только из разрешённой команды метаданных Issue или принятого настроенного действия статуса Factory с точным происхождением Issue, Work, Run и действия. Само наличие связи или редактирование комментария не публикует статус. Принятые обновления бизнес-статуса отражаются в Issue через их авторитетные записи; вручную выбранный статус задачи остаётся организационными метаданными, а не Factory Decision. Первые эффекты GitHub используют существующий маппинг Reporter управляемых меток и необязательного open/close. Произвольная удалённая запись названия, ответственного, приоритета или компонента не объявляется, пока установленный адаптер не поддерживает точный контракт. Значения для пользователя вроде `approved` — конфигурация, а не привилегированные перечисления домена.

Повторно используются существующие outbox отчётности, защитные маркеры, порядок управляемых полей, наблюдение после неизвестного ответа и ограниченное согласование. Сохраняются желаемое значение, наблюдаемое значение и идентичность маппинга и действия; неуправляемые поля не затрагиваются. Замена маппинга влияет на новые проверенные намерения, но не на цель или эффекты уже зафиксированной операции. Текущий отзыв прав по-прежнему запрещает отправку. Удалённое расхождение либо согласуется по ранее разрешённой политике управляемого поля, либо становится явным конфликтом. Решение оператора — новое разрешённое желаемое состояние или обновление маппинга с предусловием. Кнопка безусловного повтора с перезаписью не добавляется. Эхо pull или повторная квитанция проекции не создают новое выполнение, комментарий или логическое действие статуса.

Бизнес-статус Issue, состояние выполнения и состояние синхронизации независимы. Показываются направление, последнее успешное наблюдение, ожидающие операции и безопасные причины блокировки, конфликта или исчерпания попыток. Внешнее удаление, недоступный ресурс, ограничения частоты и отсутствие прав чтения или записи не уничтожают локальный Issue и историю принятого выполнения. Нельзя обещать атомарное обновление всего провайдера или полную двустороннюю синхронизацию. Застрявший push не может блокировать несвязанные ручные задачи или откатывать принятые результаты.

Рассмотренная альтернатива: общее зеркалирование по правилу «последняя запись побеждает». Отклонена, поскольку внешние API различаются, конкурентное редактирование нормально, а зеркало скрывало бы, кто управляет выполнением и результатами.

### 5. Проекции карточки сохраняют точные свидетельства и безопасный прогресс выполнения

Чтение проходит по цепочке Issue -> запросы выполнения -> Work -> существующие Run, вложенные Flow Run, циклы, Node Attempt, Build и Job. Все активные выполнения, выбранное историческое выполнение и ожидающий приём показываются раздельно. Фактический AI-профиль выполнения и модель раскрываются только при наличии сохранённых данных и прав, вместе с зарегистрированным Agent и runtime, когда они назначены. Выполнение в очереди, параллельное, недоступное и историческое выполнение обозначаются явно; ответственный и текущая модель не выдумываются. Управление профилями ролей остаётся необязательным, а идентичность рабочего Agent сохраняет существующее значение.

В карточке есть разделы Overview, Activity, Runs, Results и Actions; обсуждение находится в Activity. Список задач предлагает ограниченные фильтры по Project, статусу, приоритету, источнику, выполнению и синхронизации, а также вход в ручное создание. В основной навигации понятные ключи и безопасные краткие названия заменяют непрозрачные строки Work. Это ориентированный на задачи вход внутри существующей оболочки Console. Реализация повторно использует нынешнюю навигацию списка и подробностей, не переделывая посторонние разделы или canvas Factory.

#### 5a. Зафиксировать компоновку и контракт свойств до реализации экранов

[Руководство](https://multica.ai/docs/tutorial) и [представление Issue](https://multica.ai/docs/issues) Multica используются как образцы удобства. Результат — рабочее пространство задачи с постепенным раскрытием деталей, а не список сырых агрегатов. Следующая компоновка входит в контракт приёмки; сценарии компонентных и браузерных тестов должны покрывать её до реализации:

```text
Существующая навигация / список задач
  Project > TASK-42     Название       Бизнес-статус      Запустить pipeline
  Обзор | Активность | Запуски | Результаты | Действия
  +------------------------------------------------+------------------------+
  | Обзор: описание и критерии приёмки             | Свойства               |
  | Редакция и явное редактирование/сохранение     | статус, приоритет,     |
  | Родитель/подзадачи и недавняя активность       | ответственный, тип,    |
  |                                               | компонент, размер,     |
  | Активность: комментарии и безопасные ссылки    | метки, срок            |
  | Запуски: выбор -> этапы -> события/логи        | Сводки выполнения:     |
  | Результаты: PR/MR | Проверки | Артефакты        | профиль, модель, worker|
  | Действия: точные ожидающие защищённые команды   | PR/MR, источник/синк   |
  +------------------------------------------------+------------------------+
```

По умолчанию открывается Overview с предпросмотром недавней Activity. Шапка сохраняет видимыми понятный ключ и название, бизнес-статус и явное действие запуска. Runs и Results сохраняют выбранное выполнение и кандидата при навигации и перезагрузке, отличая исторический выбор от текущего состояния задачи. Сводки выполнения справа перечисляют все активные Run, включая ожидающие и неназначенные; единственный активный агент не выдумывается. Краткие сводки PR ссылаются на ту же проекцию Results, а не на отдельного наблюдателя. Технические ID, дайджесты и расширенные представления Run/Build доступны через Details и копирование, а не как основные подписи или обязательные свободные поля ввода.

На узких экранах содержимое выстраивается вертикально; панель Properties доступна с клавиатуры и открывается явной кнопкой. Сохраняются управление статусом и запуском, выбранный исторический объект и доступ ко всем разделам. Настольные колонки не сжимаются в горизонтальную прокрутку. На английском и русском покрываются сценарии новой ручной задачи без Run, подготовки, очереди, параллельного и активного выполнения, ошибки, ожидания человека, завершения, устаревших данных провайдера, просроченного артефакта и запрещённого раздела. Независимый сбой раздела сохраняет видимые устаревшие данные и не должен выглядеть как пустая задача.

| Свойство | Редактирование и смысл |
| --- | --- |
| Project и понятный ключ | Владеющий Project и выделенная сервером идентичность; общего переноса между Project нет |
| Название, описание, приёмка | Версионируемые требования; приёмка может оставаться неполной до проверки запроса выполнения |
| Бизнес-статус | Закреплённый workflow Project; меняется только общей командой перехода |
| Приоритет | Ограниченное значение планирования Project; последующее редактирование не меняет принятое намерение планирования |
| Ответственный | Необязательная ссылка на организационного ответственного, разрешаемая сервером; отделена от фактического авторства действий, AI-профиля и зарегистрированного исполнителя |
| Тип, компонент, размер | Необязательные ограниченные варианты Project; размеры S/M/L/XL — примеры редактируемых значений, а не поведение домена |
| Метки и срок | Необязательные идентификаторы меток Project и дата без времени для планирования; не являются Source, расписанием или триггером выполнения |
| Дополнительные свойства | Ограниченные определённые Project значения: обычный текст, конечный выбор, boolean, число или дата; без формул, вложенных объектов и исполняемых выражений |
| Родитель и подзадачи | Необязательный единственный родитель в том же Project и дочерние задачи с пагинацией; ссылки на себя, циклические, скрытые и чужие связи отклоняются; зависимости выполнения и свёртка статусов не добавляются |
| Создано/обновлено и создатель | Сохранённые временные отметки и фактическое происхождение действий только для чтения; сервис или неизвестный actor не переименовывается в автора-человека |
| Источник, синхронизация, профиль/модель, worker | Наблюдаемые факты только для чтения с актуальностью и недоступностью; credentials и сырые пути установки отсутствуют |

Определения и варианты свойств, конечные ограничения количества, байтов и значений публикуются через разрешённые настройки Project и генерируемые контракты. Сохраняются версии определений и вариантов, необходимые для чтения старых редакций; выведенные из использования значения остаются объяснимыми, а не переименовываются молча и не удаляются из истории. Редактирование свойств использует текущие предусловия Issue и определения, повтор в своей области и владение источником. Значения планирования по умолчанию локальны. Маппинг Source может управлять полем только при явно поддерживаемых направлении и разрешении, а не просто потому, что поле есть в карточке. Изменение планирования не создаёт Work, операцию провайдера или переход статуса. Поле, явно включённое в требования выполнения, участвует в происхождении зафиксированного входа; посторонние метаданные не делают привязку требований принятого действия недействительной.

Варианты ответственного берутся из разрешённых сервером идентичностей, уже доступных в развёртывании. Доступность каталога указывается явно. Без каталога людей предлагается Unassigned, фактические действия сервиса или оператора показываются честно, а создание, редактирование и запуск остаются доступны. Нельзя выдумывать пользователей, считать principal шлюза человеком или вводить регистрацию, входящие очереди и управление разрешениями. Назначение не даёт доступ и никогда не запускает агента. Выбор роли и профиля остаётся частью явной проверки выполнения. Связи родитель/потомок и пользовательские свойства служат организации, а не образуют ещё один движок workflow.

#### 5b. Подробный журнал выполнения на основе реальных сохранённых наблюдений

Представление Runs содержит выбор выполнения с редакцией требований, pipeline и целью, исходом и временем; иерархию этапов и Job со статусом, длительностью и повторами; ограниченную панель подробностей событий и логов. Строки идентифицируют этап и Node Attempt, обычные Build, Attempt и Job, а также worker, если он известен. Показываются исходные время начала и окончания, прошедшее время и время в очереди, поддерживаемые факты о действующих модели и профиле, измеренные токены и стоимость, безопасные сводки ошибок и исходов. Отсутствующие измерения — Unknown, а не ноль; зарезервированные лимиты и фактическое использование различаются.

Повторно используются диагностика Run, структурированные публичные события выполнения и доступные по правам читатели логов. События могут раскрывать смену состояния жизненного цикла, безопасные публичные сводки агента, название инструмента, разрешённый предпросмотр команды с удалёнными чувствительными данными, файловую операцию относительно рабочей области, статус завершения или код выхода и связанный вывод. Сырые аргументы команд, значения окружения, приватные промпты, защищённые тесты, credentials, транскрипты и скрытые рассуждения не являются общими данными временной шкалы. Строки сводок событий хранят ссылки; чувствительный доступный по правам вывод загружается при раскрытии через существующего отдельного читателя и политику no-store и удаления чувствительных данных. Текст модели и старые логи не разбираются в авторитетные события инструментов или результаты проверок.

При необходимости первый проверяемый адаптер выполнения инструментируется через существующий канал событий и логов, чтобы тесты на уровне процессов доказывали поступление реальных событий команд и файловых операций в это представление. Добавляются только ограниченные метаданные событий, нужные читателю; новая версия протокола Agent, параллельный журнал выполнения и планировщик не создаются. Для инструментов и backend, которые не сообщают категорию деталей, показывается Not reported и сохраняется переход к сырым доступным по правам логам; шаги не выдумываются. Первый поддерживаемый подробный путь проверяется, остальные ограничения возможностей указываются честно.

Стабильная идентичность потока, последовательность или курсор и точная привязка выполнения позволяют переподключение и ограниченное живое наблюдение без дублей и молча пропущенных интервалов. Повторно используется инфраструктура пагинации и наблюдения временной шкалы; загрузка старых записей не скачивает весь Run. Живое наблюдение останавливается или замедляется при скрытом представлении и завершённом выполнении, сохраняет прокрутку и выбор пользователя, явно отмечает разрывы, устаревший хвост и просроченное содержимое. Отмена, повтор и ответ используют существующие команды с точной целью. Просмотр или раскрытие строки не вызывает инструмент и не записывает данные провайдеру.

#### 5c. Проекции code review, проверок и артефактов без новых полномочий

Один Issue может ссылаться на несколько PR/MR отдельно от своего нуля или одного основного внешнего тикета. Сохраняются канонические ссылки code review с идентичностью установленного провайдера, нативного репозитория и review, владеющим Project, происхождением связи и точными выполнением и кандидатом, если связь подтверждена. Провайдеры code review и тикета могут различаться. Доверенная квитанция Delivery может предоставить ссылку. Явное присоединение выбирает разрешённые репозиторий и нативное review и требует проверки текущих предусловий. Название или ветка с ключом задачи и произвольный URL остаются лишь возможной подсказкой до подтверждения проверенной связи. Они не могут объединять истории, загружать данные с произвольного endpoint или доказывать, какой кандидат выполнялся.

Добавляется нормализованный порт наблюдения code review только для чтения поверх существующего механизма установленных адаптеров и подключений. Совместимые наблюдатели переиспользуются; если чтения review и проверок нет, контракты расширяются через TDD. Нельзя считать, что права Delivery или чтения тикетов покрывают их автоматически. Разрешение отдельно ограничивается фактическим репозиторием кода. Этот change отвечает за проверку конкретного адаптера чтения GitHub и второго тестового адаптера с другой терминологией; нативные адаптеры GitLab/Jira остаются за рамками. Новая форма токена, SDK провайдера в ядре Issue, второй механизм credentials и общий webhook/poller не вводятся. Обновление использует существующие ограниченные механизмы supervision, наблюдения, повторов и видимости. GET карточки выдаёт сохранённые наблюдения без вызовов провайдера.

Карточки PR/MR показывают провайдера и репозиторий, номер и название, доверенную внешнюю ссылку, автора при наличии видимости, состояние draft/open/closed/merged либо недоступность, head/base-ревизии, доступные количества изменённых файлов, добавлений и удалений, сводку review, агрегат проверок и время наблюдения. Неподдерживаемые счётчики и факты review остаются недоступными. Наблюдения сохраняются отдельно для каждого review и ревизии; движение head PR не может переобозначить кандидата или проверки старого выполнения. Состояние merge информационное и не даёт полномочий на merge/deploy или изменение статуса Issue. При недоступности провайдера сохраняется последнее известное наблюдение со Stale/Blocked; ручные задачи и результаты остаются доступны.

Results содержит панели PR/MR, Checks и Artifacts с отдельной пагинацией. Проверки отличают верификацию и свидетельства Factory от внешнего CI, сохраняют точное выполнение и кандидата либо head-ревизию review, производителя и название, состояния pending/running/pass/fail/cancelled/skipped/indeterminate/unavailable, время и доступные по правам ссылки на детали и логи. Показываются обязательные проверки, которые отсутствуют или ещё не наблюдались, а не только сообщённые успехи. Внешний CI или merge не являются Factory Decision. Новая head-ревизия или другой кандидат делают прежнюю проверку исторической. Агрегированный статус указывает покрытие и не может выводить общую приёмку из неполной страницы.

Артефакты группируют исходные входные ссылки, выходы кандидата и сборки, отчёты верификации и review и снимки экрана по точным производящим выполнению, Build, Job и объекту проверки. Показываются безопасное название, вид и тип содержимого, размер, дайджест и происхождение в Details, публикация, хранение и доступность, явные действия открытия и скачивания. Входы Project сохраняют реальное происхождение и не становятся произведёнными свидетельствами. Повторно используются разрешённые читатели и разрешения скачивания, а также ограниченный предпросмотр текста или проверенных PNG/JPEG/WebP по запросу. Нельзя выполнять HTML/SVG/скрипты, напрямую подгружать контент провайдера или раскрывать защищённые и приватные выходы через миниатюру или общий список имён файлов. Просроченное или не сохранённое содержимое остаётся недоступной ссылкой и не восстанавливается открытием карточки. Это просмотр выходов, а не новая система загрузок или вложений комментариев.

Рассмотренные альтернативы: встроить страницу issue провайдера, выгрузить все логи выполнения или использовать один зелёный индикатор задачи. Отклонены, поскольку теряются независимость от провайдера, ограниченный доступ и точные различия объекта проверки и приёмки. Карточка объединяет существующие источники полномочий через специализированные проекции чтения.

Настройки Project показывают названия и порядок статусов, один выбор начального статуса и отдельный множественный выбор завершающих на уровне workflow, разрешённые рёбра и источники команд, поддерживаемые требования к свидетельствам. Замена неизменяема и проходит проверку; принятие новой версии явно. Карточка показывает только текущие переходы, разрешённые сервером, их ожидаемую версию, причины владения и недоступности. История статуса отделена от прогресса Run и синхронизации. Существующее редактирование Flow добавляет явные действия статуса Issue на объявленных маршрутах исходов, не создавая второй canvas. Проверка маппинга связи источника — отдельное представление внутреннего статуса, нативных наблюдений и эффектов и владения полем; оно не заменяет редактирование workflow Project. Все три представления используют ограниченные генерируемые варианты, проверку текущей версии, клавиатуру и фокус, английские и русские подписи и черновики только в памяти. Выбор статуса или завершающего статуса workflow не может подаваться как полномочие approve/deploy.

Results привязывает каждого кандидата, отчёт свидетельств, оценку и Decision к исходному выполнению. Позднее завершённый triage не стирает предыдущую ошибку реализации, а успех проверок прежнего кандидата не удовлетворяет требованиям нового. Техническое завершение, полнота верификации и приёмка разделяются. Текст модели и комментарии не могут утверждать, что проверки прошли. Ссылки на логи используют существующих разрешённых читателей Build и логов; приватные транскрипты и скрытые рассуждения никогда не собираются во временную шкалу задачи.

Ограничения задаются для разделов карточки независимо. Страницы выполнений и проверок привязываются к отметке авторитетной истории, редакции Issue и выбранному выполнению; у обсуждения своя последовательность внутри Issue. Детерминированный порядок временной шкалы включает время, тип источника и стабильную идентичность записи. Карточка сообщает наблюдение и неполное или устаревшее покрытие по разделам, а не атомарный снимок всех внешних систем. Общий успешный статус нельзя выводить из части страниц или последнего завершённого Run.

### 6. Обсуждение отделено от выполнения; действия операторов сохраняют точную привязку

Сохраняется исходная граница обсуждения только для операторов, теперь принадлежащая Issue. Комментарии — обычный текст только на добавление, не более 16 384 байтов UTF-8 и 1 000 комментариев за всё время жизни Issue либо более строгие настроенные ограничения, с одним уровнем ответов внутри того же Issue. Последовательность выделяется атомарно, сохраняются повтор в своей области, безопасный аудит и метаданные хранения и запрета удаления. Известные чувствительные шаблоны отклоняются; отдельное чтение тела и ограничение доступа остаются необходимыми, поскольку обнаружение неполно. Авторство соответствует выпуску с доверенной сетью, а не выдуманным аутентифицированным учётным записям. Сырой текст не попадает в общий аудит, курсоры, логи, аналитику, URL и данные очередей.

Комментарии никогда не вызывают агента, не меняют Work, не становятся свидетельством или подтверждением и автоматически не попадают в Context модели. Уточнение использует явно выбранный объявленный ответ human gate и существующий endpoint управления. Синхронизация внешних комментариев и разговорные команды агентам остаются отдельной будущей работой.

Для общей очереди действий Project и глобальной очереди повторно используется чистый текущий дескриптор допустимости управления. Каждый элемент сохраняет точную связь с Issue при наличии, а также идентичности Work, Run, Flow, цикла, попытки, контракта и кандидата, сроки, допустимые ответы и наблюдаемую версию Run. Разрешением владеет существующий версионируемый механизм управления с `Idempotency-Key` и `If-Match` Run; версия Issue их не заменяет. Общие endpoint «одобрить Issue», «закрыть элемент очереди» и массового переопределения жизненного цикла не добавляются.

Сохраняется индексируемая производная проекция действий с транзакционной инвалидацией, возобновляемым ограниченным дозаполнением и защитой по версии источника. Остановленный worker модели чтения сообщает неполное покрытие, не блокируя выполнение. До вычисления количества, порядка и курсоров чтение повторно проверяет видимость, срок и версии источника. Записанное намерение больше не считается неотвеченным. Обработка владельцем остаётся отдельной от принятия команды. Конкурирующие ответы допускают не более одного намерения; точный повтор победителя сохраняет силу после дальнейшего прогресса. Изменение метаданных Issue не может перенаправить ожидающий ответ на другое выполнение.

Создание подключений, разрешений и маппингов использует существующие границы интеграций и управления определениями; типизированные действия статуса Issue в pipeline — существующую публикацию Flow. Маршруты Issue не принимают сырые токены и произвольные данные провайдера. Записи Issue требуют собственной регистрации разрешённых действий и ресурсов, повтора в своей области и строгих предусловий текущих редакции, связи и статуса. Администрирование workflow, ручное перемещение статуса, действия статуса pipeline и маппинг статусов источника требуют соответствующих отдельных полномочий; права редактирования и обсуждения Issue их не предоставляют. Команды выполнения дополнительно требуют обычных прав приёма и проверки точной цели. Маршруты бизнес-переходов не могут разрешать human gate выполнения или подменять предусловия Run версиями Issue. GET никогда не создаёт и не дозаполняет Issue, не отправляет обращения провайдерам и не резервирует выполнение.

Отдельные чтения тела описания, редакции и комментария применяют no-store и независимую проверку видимости. Сводки списка и карточки и операционные записи возвращают только безопасные метаданные и ссылки, а не тела задач, промпты, скрытые тесты, транскрипты провайдера, credentials и приватные URL передачи. Генерируемые ограниченные схемы определяют проверку и варианты Console. Чувствительные черновики и подтверждённые ключи запросов остаются только в памяти компонента. Сохраняются текущие контракты отсутствия персистентного хранения в клиенте, состояния запросов, клавиатуры и фокуса, узкой компоновки и английского и русского языков.

Публикация определений свойств использует существующий шаблон разрешённых настроек Project и версионируемых определений с явными правами администрирования и повтором. Редактирование родителя, ответственного и свойств использует границу редактирования Issue; статус остаётся командой перехода. Чтение журнала, review, проверок и артефактов привязывает выбранные выполнение, редакцию и видимость до вычисления количества и курсоров. Для отдельных тел и выходов сохраняются собственные политики читателей. Присоединение review — команда метаданных с независимыми полномочиями чтения репозитория, а не разрешение менять платформу разработки или состояние задачи.

После связывания идентичность Issue публикуется как добавочные метаданные новых представлений приёма и Run. Существующие маршруты Run, управление и приём Artifact остаются доступны, в том числе до включения необязательных возможностей Issue. Канонический маршрут карточки — `/issues/{issue_id}`. URL могут выбирать вкладки и точные ID выполнения, но никогда не содержат тела и значения команд. Создание только Issue работает при ненастроенной Factory.

### 8. Общие предварительные условия без расширения соседних change

В этом change сохраняются три существующих пути возможностей. Наблюдения Source, связь с Issue и обработка управляемых эффектов реализуются через общие точки расширения рядом с существующими приёмом и отчётностью. Требование приёма dark-factory и инвариант одного Run не меняются. Текущее поведение GitHub остаётся базой совместимости. Поддержка нативных GitLab/Jira доказывается как граница расширения вторым тестовым адаптером, а не объявляется поставленной интеграцией.

Архивированный `add-github-work-source` предоставляет разрешения подключений, проверки провайдера, настройку входов и эффектов источника, необязательные контракты наблюдений. Конкретные установленные предварительные условия сначала характеризуются; завершённые пункты не открываются заново и работа с живым GitHub не считается проверенной — её статус остаётся неподтверждённым. Этот change владеет внутренними workflow статусов, явными действиями статуса Issue и отдельной синхронизацией полей и статусов. Ручные сценарии Issue и workflow не требуют этих условий провайдера. `add-factory-bugfix-quickstart` по-прежнему отвечает за свой preset и интерфейс готовности. Его восстанавливаемая публикация текстового входа Project — одна общая точка: сначала характеризуется или выделяется существующее поведение; если его нет, оно реализуется здесь, а последующее согласование записывается в quickstart до его реализации. `add-factory-role-profiles` позже может предоставить подписи профилей, не делая каждый Issue зависимым от него. Файлы планов соседних change в этом обновлении не редактируются.

[Исследование задачи 1.2](verification-1.2.md) фиксирует конкретные границы повторного использования и недостающие части. Общая публикация текста Project относится здесь к задачам 3.2–3.3; quickstart использует ту же операцию, а не публикует второй журнал приёма. Проверка включает композицию читателей входов в runtime, подписанную передачу и хранение. Одна лишь поддержка читателя Source на уровне application не доказывает полный путь выполнения. Установленные технические профили выполнения остаются отличными от будущих редактируемых определений ролей и профилей.

## Риски и компромиссы

- **Редакции Issue могут скрыть требования, по которым шло выполнение** -> Сохранять неизменяемые ссылки редакции и входов для каждого запроса; явно помечать новые описания и исторические результаты.
- **Конкурирующие импорты могут разделить одну задачу** -> Обеспечить уникальность нативной связи в её области и идемпотентное атомарное связывание; никогда не дедуплицировать по названию или ключу pipeline.
- **Изменяемый статус задачи может выглядеть как приёмка** -> Отделять метаданные задачи от авторитетных Decision Run и точных проверок в API и UI.
- **Старые или параллельные выполнения могут переместить обновлённую карточку** -> Защищать явные действия зафиксированными требованиями и workflow, применимостью статуса и сохраняемой цепочкой команд; устаревшие команды конфликтуют, не отменяя принятое выполнение.
- **Политика Project может измениться под активными задачами** -> Закреплять версии workflow и требовать явного проверенного принятия; сохранять идентичности, историю и маппинги, на которые есть ссылки.
- **Маппинг нативных статусов может стать ещё одним workflow** -> Оставлять его преобразованием с заданным владельцем поля через одну команду перехода; отклонять неоднозначных, запрещённых и перекрывающихся производителей записей.
- **Приём и связь с Issue могут фиксироваться отдельно** -> Сохранять исходную идентичность запроса и приёма и согласовывать связь после перезапуска без нового Work.
- **Внешнее состояние меняется во время записи** -> Использовать существующие защитные маркеры Reporter, наблюдаемые ревизии и ограниченное согласование; показывать конфликты там, где нативные атомарные предусловия недоступны.
- **У старой истории неполная идентичность или сохранность содержимого** -> Дозаполнять только проверенные нативные связи; иначе использовать один Issue на Work и помечать недоступные поля. Нельзя угадывать или восстанавливать просроченные тела.
- **Расширенная модель задачи может стать ещё одним оркестратором** -> Ограничить Issue замыслом, редакциями и связями; всё выполнение и допустимость остаются у нынешних владельцев.
- **Удобная карточка может обещать неподдерживаемые данные и действия** -> Проверять реальных производителей событий и review, раскрывать отсутствующие возможности и устаревшее покрытие, различать организационного ответственного, runtime-worker, внешний CI и приёмку Factory.

## План миграции

1. Запустить текущие регрессии приёма, Source/Reporter, публикации входов, управления и Console. До рефакторинга общей точки добавить характеризующие тесты там, где покрытия нет.
2. Через добавочные миграции, безопасные при повторном запуске, и узкие порты хранилища с паритетом memory/PostgreSQL добавить workflow и выбор по умолчанию Project, Issue, редакции, ключи, историю статуса, связи с источником, запросы выполнения, связи и применимость, метаданные обсуждения, повторов и производных действий. Декларативный вариант по умолчанию должен быть доступен без провайдера, настройки Factory и дополнительных прав первого создателя. Сохранить все ID Work/Run, ограничения уникальности и журналы.
3. Дозаполнять сохранённые Work ограниченными возобновляемыми пакетами: группировать только проверенные одинаковые нативные идентичности внутри одного Project и области безопасности, иначе создавать один Issue на Work. Использовать безопасные сохранённые метаданные названия или явную заглушку недоступности, а не внешнюю идентичность как выдуманные требования. Дозаполнение не создаёт приём, вызовы провайдера, credentials, эффекты статуса и обсуждение. Первая дозаполненная редакция не утверждает, что каждый связанный Work использовал её содержимое. Точные прежние Artifact Work остаются источником истины для его входов выполнения.
4. Сначала включить ручное создание и редактирование Issue и восстанавливаемое выполнение. Повторно использовать ту же точку публикации текста и приёма, что и quickstart, и проверить старых клиентов Artifact/Run. Затем подключить необязательный импорт источника, постоянное обновление связей и существующую отчётность; до явной разрешённой настройки они отключены.
5. Предоставить через генерируемые REST/Console настройки workflow Project, точные действия и историю статуса, отдельную проверку маппинга источника, навигацию задач, ссылки старых Run на Issue и общие действия с честным отображением дозаполнения и покрытия. Старые карточки инициализировать начальным статусом проверенного workflow или варианта по умолчанию, а не угадывать по последнему Run. Сам факт создания карточки миграцией не настраивает автоматическое выполнение, переход или синхронизацию.
6. Применять отдельные правила хранения содержимого Issue и обсуждения вместе с точными сроками хранения входов выполнения и запретами удаления. При необходимости сохранять метаданные связей и повторов, не восстанавливая просроченные описания, комментарии, снимки провайдера и логи. Включить ожидающие запросы, нативные связи и состояние отчётности в резервное копирование и восстановление.
7. Откатывать отключением новых записей Issue, импорта, отправки синхронизации и UI, сохраняя совместимую очистку и состояние ожидающих намерений. Существующие прямые операции Factory/Build продолжают работать. Нельзя возвращаться к бинарному файлу, который отправляет обращения провайдерам, игнорируя сохранённое владение и защитные маркеры. Новая история не удаляется ради отката.

## Стратегия проверки

Использовать публичные контракты application и HTTP с паритетом memory/PostgreSQL, тестовые адаптеры Source/Reporter и компонентные и браузерные сценарии Console. Проверять ручные задачи без Factory и провайдеров; конкурентные изменения и импорты; несколько выполнений точных редакций; неизменность старого повтора приёма; прерывания публикации, приёма и связывания; устаревшие внешние наблюдения; конфликты управляемых полей и записи с неизвестным результатом; отзыв прав и ограничения частоты; отсутствие выполнения от эхо-обновлений; привязку свидетельств; изоляцию комментариев; восстановление защищённой очереди; видимость, хранение и резервное копирование.

Проверить переименованные пользовательские статусы и рёбра, начальные варианты по умолчанию, неизменяемую замену и принятие workflow, запрещённые и ручные переходы и переходы под управлением источника, настроенные требования свидетельств и завершение Run без действий. Покрыть последовательные действия одного выполнения, конкурирующие и запоздавшие Run, изменённые требования и возврат статуса к прежнему значению. Повтор должен сохранять одну квитанцию статуса без переписывания принятого выполнения. Проверять отдельные полномочия исходящего, входящего и несинхронизируемого статуса, несопоставленные и неоднозначные наблюдения, запрещённые внешние рёбра, неподдерживаемые переходы провайдера и перекрытие с существующими прямыми эффектами источника. Triage может достичь Ready или Declined только через настроенное действие, но не Done лишь потому, что его Run завершился.

Сквозной пилот создаёт ручную задачу, редактирует её, запускает один настроенный pipeline, меняет задачу, пока исходный Run сохраняет снимок, и запускает последующее явное выполнение под той же карточкой. Отдельная импортированная задача проходит входы оценки и реализации, получает принятые настроенные эффекты источника и сохраняет успешное выполнение, пока внедрённый сбой провайдера показывает ожидающую синхронизацию. Включить объявленный ответ человека и инфраструктурную повторную попытку, повтор и перезапуск, проваленные и неопределённые свидетельства и вторую независимую от провайдера тестовую реализацию. Живая платная модель и нативные учётные записи GitLab/Jira для этих контрактов не нужны; реальная проверка поддерживаемого адаптера остаётся явной.

Оба пилота проверяют заданную настольную и узкую карточку, необязательные свойства без каталога пользователей, видимость родителя и отклонение циклов, подробную проверенную трассу выполнения, выбор истории и живое переподключение. Импортированный пилот дополнительно показывает проверенную связь review, изменившуюся head-ревизию PR с историческими проверками, независимый отзыв чтения review, устаревшие метаданные review и точный предпросмотр и истечение срока артефакта. Браузерные проверки подтверждают фактическое поведение собранного API и осмысленные подписи, а не только снимки экрана или поддельные полностью зелёные сводки. Выполненные подготовительные задачи 1.1–1.2 остаются выполненными; их исторические базовые проверки не подтверждают новые возможности журнала, review и предпросмотра, которым нужны собственные Red/Green.

Любая наблюдаемая реализация, тестовый сценарий, конфигурация и миграция проходят осмысленный Red/Green через публичную границу до изменения реализации. Для рефакторинга сначала проверяется текущее поведение, фиксируются точные команды и результаты. Эта редакция только планирования не имеет исполняемого поведения; вместо этого проверяются OpenSpec, форматирование и согласованность артефактов.
