## Зачем

Операторам нужна одна постоянная задача, которая объединяет требования, внешние тикеты, запуски Factory, текущий прогресс и результаты. Карточка, привязанная к одному неизменяемому Work, не может представить ручные черновики, последующие изменения или оценку и реализацию, выполняемые разными pipeline.

## Что меняется

- Вводится принадлежащая Project сущность **Issue** со стабильным внутренним идентификатором, понятным человеку ключом, редактируемыми версионируемыми требованиями и метаданными, необязательной связью с внешним источником и историей связанных запусков. Ручное создание и редактирование работают без провайдера, credentials, репозитория или настроенного pipeline Factory; для выполнения действуют отдельные предварительные условия.
- Добавляются версионируемые бизнес-workflow Project со стабильными идентификаторами статусов и переходов, редактируемыми названиями, полями `initial_status_id` и уникальным набором `terminal_status_ids` на уровне workflow, а также явно разрешёнными переходами. Записи статусов содержат только ID и название; выбор начального и завершающих статусов относится к настройкам workflow. Предоставляется редактируемый вариант по умолчанию, чтобы первая ручная задача не требовала настройки workflow. Ручные команды, принятые действия pipeline и разрешённые входящие изменения из источника используют одну общую границу проверки переходов; обычное редактирование метаданных не может её обойти.
- Для выбранных объявленных исходов pipeline настраиваются явные действия изменения статуса Issue. Фиксируются workflow, переход и точное происхождение выполнения; устаревшие или конкурирующие обновления отклоняются, история сохраняется идемпотентно. Завершение Run, названия этапов и текст модели никогда не определяют статус задачи или приёмку выполнения автоматически.
- Предложенная карточка одного Work заменяется постоянной карточкой задачи. У одного Issue может быть много неизменяемых Work Envelope, и у каждого сохраняется существующий единственный Factory Run. Явные запросы выполнения фиксируют выбранную редакцию Issue и точную цель Factory; повторная попытка остаётся в исходном Run. Существующие идентификаторы и URL Work/Run сохраняют силу.
- Импорт и обновление задач используют установленные возможности Source, независимые от провайдера. Явно управляемые поля синхронизируются через версионируемые маппинги, поддерживаемые возможностями адаптера, и существующее восстановление Reporter. На первом этапе у Issue может быть ноль или один основной внешний источник. Сохраняются нативная идентичность, владение полями, конфликты, актуальность и независимо ограниченные разрешения на чтение и запись. GitHub — первый конкретный адаптер; GitLab и Jira должны укладываться в тот же контракт, не становясь зависимостями или обещанными реализациями.
- Маппинг внешних статусов отделяется от workflow Project и действий pipeline. Стабильные внутренние ID статусов сопоставляются с поддерживаемыми нативными значениями и эффектами, либо нативные наблюдения с явно заданным владением сопоставляются с разрешёнными внутренними переходами. Для каждого поля задаются один владелец и направление синхронизации; несопоставленные, неоднозначные и запрещённые переходы видны пользователю. Предотвращаются эхо-обновления и конкурирующие источники записи.
- Бизнес-статус задачи, состояние выполнения, текущий AI-профиль при его наличии, зарегистрированный исполнитель и состояние синхронизации показываются раздельно. Отображаются точные результаты Run, этапов и Build, текущие и исторические проверки, безопасная активность и ссылки на доступные по правам логи. Приёмка не выводится из текста агента.
- Карточка становится основным рабочим пространством оператора: постоянная шапка, описание и Activity в основной колонке, свойства и сводки выполнения справа, отдельные представления Runs, Results и Actions. Задаются настольная и узкая компоновки, пустые состояния, загрузка, устаревшие данные и точная навигация по истории; технические формы конфигурации не используются как интерфейс задачи.
- Добавляются конкретные свойства планирования: организационный ответственный, срок, метки Project, настраиваемые тип, компонент и размер, ограниченные простые пользовательские поля, а также связи родительской задачи и подзадач внутри одного Project. Эти метаданные необязательны. Назначение, даты и связи не создают выполнение, разрешения или неявную приёмку.
- Показывается подробный сохраняемый журнал запуска: прогресс этапов и Job, доступные безопасные события инструментов и файловых операций, время, измеренное использование ресурсов, ошибки, сводки результатов и доступная по правам детализация логов. Добавляются независимые от провайдера карточки PR/MR, внешние проверки с привязкой к ревизии и сгруппированные доступные по правам артефакты с предпросмотром. Проверяется реальная генерация событий и адаптер чтения GitHub code review с дополнительным тестовым адаптером, использующим другую терминологию. Наличие URL или установки только с метаданными не считается подтверждением возможностей.
- Сохраняются ограниченное обсуждение только для операторов и общая очередь операторских действий с точной привязкой к объектам. Комментарии не вызывают агентов и не становятся Context выполнения; уточнения и подтверждения по-прежнему используют объявленные защищённые команды управления.
- Добавляются REST и ориентированный на задачи сценарий Console: создать задачу, отредактировать требования, выбрать pipeline, проверить зафиксированный запрос, начать выполнение, следить за прогрессом и вернуться к той же задаче для нового запуска. Интеграции выбираются по доступным по правам ссылкам на подключения и ресурсы; credentials никогда не попадают в формы задачи или pipeline.

## Возможности

### Новые возможности

- `server/factory-work-collaboration`: постоянные Issue, свойства и связи планирования, настраиваемые workflow статусов Project, защищённые ручные переходы и переходы от pipeline/источника, неизменяемая связь редакции с Work, отдельные маппинги внешних статусов, обсуждения операторов, подробные журналы выполнения, точные проекции code review, проверок и артефактов, обнаружение решений, требующих действий.

### Изменяемые возможности

- `server/rest-control-plane`: добавить версионируемые варианты workflow и свойств Project, варианты переходов, их историю и команды, публикацию типизированных действий изменения статуса Issue, создание и редактирование Issue и их связей, запросы выполнения, привязку источников и синхронизацию, ссылки на code review с ограниченной областью доступа, ограниченные чтения журналов, проверок, артефактов, обсуждений и очереди, а также генерируемые контракты. Существующее управление Factory сохраняется.
- `ui/operator-console`: добавить настройки статусов и свойств Project, явную настройку действий изменения статуса Issue в pipeline и отдельный просмотр маппинга внешних статусов, а также заданную компоновку карточки, ручное создание, редактирование свойств, подробный просмотр запусков, представления PR/MR, проверок и артефактов, обратную связь о синхронизации и защищённые действия оператора.

## Влияние

- Расширяются границы application/store Factory, добавочные миграции PostgreSQL, существующая композиция Source/Reporter, сохраняемые входные данные Project, REST/OpenAPI, навигация Console и рекомендации по хранению и резервному копированию. Не добавляются новый исполнитель, протокол Agent, SDK провайдера в домене или второй владелец жизненного цикла Factory.
- Повторно используются разрешения на подключения и ресурсы, контракты неизменяемого приёма и отчётности из архивированного `add-github-work-source`. Его работа с живым GitHub остаётся неподтверждённой и не становится условием ручных задач. Workflow и действия Issue, а также синхронизация полей остаются в этом change. Повторно используется запланированная в `add-factory-bugfix-quickstart` общая точка восстанавливаемой публикации текста; при необходимости она сначала реализуется здесь, без параллельной реализации приёма. AI-профили ролей остаются необязательной интеграцией с `add-factory-role-profiles`.
- [Руководство](https://multica.ai/docs/tutorial) и [представление Issue](https://multica.ai/docs/issues) Multica используются как образцы взаимодействия, а не как обещание скопировать runtime или все возможности продукта. Существующие варианты actor/identity используются для организационного назначения, если они доступны. Развёртывание без каталога людей остаётся работоспособным с неназначенными задачами и честным указанием действий сервисов. Наблюдение за code review добавляет узко ограниченную возможность чтения там, где её нет; провайдеры тикетов и code review могут различаться.
- За рамками остаются универсальный движок скриптов workflow, автоматическая миграция workflow существующих Issue, автоматический чат и делегирование агентам, синхронизация комментариев и вложений, автоматическое создание внешних тикетов, зеркалирование одного Issue между несколькими провайдерами, неявный запуск при изменении текста или статуса, новый canvas pipeline, персональные аутентифицированные входящие очереди и дополнительные полномочия на merge/deploy. Реализация выполняется обязательными поведенческими циклами Red/Green.
