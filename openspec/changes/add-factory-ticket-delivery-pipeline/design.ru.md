## Контекст

Объем работ описан в [proposal.ru.md](proposal.ru.md). Соседний change по триажу предоставляет принятые результаты проверки допустимости и классификации, размеры `small|medium|large`, наблюдения о воспроизводимости, общий механизм разрешения пресетов и настроенные действия Reporter. Его документ завершения подтверждает только прохождение триажа. До реализации этот pipeline намеренно не доходит.

В репозитории уже есть шаблоны требований, защищенных тестов, реализации, ревью и валидации в `config/factory/flows/base-flow/`, а также соответствующие прикладные обработчики и поведенческие тесты. Сейчас `FactoryPresetHandlers` предоставляет выпущенный пресет триажа. Для сборки нового pipeline используем общую конфигурацию Flow, явные проекции Context и принятые контракты.

Сейчас Delivery поддерживает Observe, Publish и Cancel. Операция merge намеренно отсутствует в `server/protocols/octacity-delivery-protocol/src/request.rs`. Основная VCS-спецификация оставляет merge внешней ручной операцией; этот change сохраняет ее контракт. Основной контракт требований Dark Factory требует независимого ревью спецификации для крупной работы и нуждается в явном изменении для запрошенного компактного pipeline. Наличие отдельных механизмов еще не означает, что весь следующий после триажа сценарий уже работает.

## Цели и что не входит в задачу

**Цели:** собрать один рабочий пресет следующего pipeline с запрошенным порядком этапов, сохраняемой передачей результата триажа и опубликованным PR для ручного merge. На каждую применимую ответственность приходится один агентский запуск; код проверяет один независимый ревьюер. Существующие публичные компоненты расширяются только для недостающего поведения.

**Обязательные гарантии выполнения:** настроить, обеспечить и проверить изоляцию запусков и прав для каждого этапа. Это включает отдельные права на рабочие каталоги, артефакты, инструменты и команды, сеть и учетные данные, в том числе между этапами с общей ролью. Для этих гарантий используем и при необходимости расширяем существующие механизмы runtime. Неизменяемые кандидаты и восстановление также остаются обязательными контрактами выполнения.

**Не входит в задачу:** новый планировщик, отдельное хранилище жизненного цикла этапов, копирование всего base-flow, обязательная полная процедура ревью спецификаций, кворум ревьюеров, ветка исследования новых функций, автоматический merge, развертывание или новые провайдеры Git-хостинга.

## Решения

### 1. Отдельный запуск следующего pipeline с точной привязкой к результату триажа

Публикуем `config/factory/presets/ticket-delivery/` через существующие механизмы разрешения пресетов, проверки готовности и настройки. Собираем выбранные части base-flow из обычных проверок перехода, узлов Build, вложенных Flow и доверенных действий. Логические названия этапов не определяют, какой Rust-код запускается.

Включенный вход следующего pipeline получает принятый результат триажа через сохраняемые явные проекции и создает отдельные Work/Run, связанные с тем же Issue или тикетом внешней системы. Явный запрос запуска Issue использует тот же входной контракт. При необходимости расширяем существующие подготовку и допуск привязкой к результату предшественника; дополнительную очередь или журнал не создаем. Сохраняем тип, размер, допустимость работы, доказательства воспроизведения, исходное ожидаемое поведение и выбранный объект работы с кодом. Несовпадения источника или объекта работы отклоняем. Существующий стабильный идентификатор входа обеспечивает дедупликацию при опросе и перезапуске; изменение меток не создает новую попытку. Прием в этот pipeline включается один раз при настройке, независимо от триажа.

Рассмотренная альтернатива: неявный запуск сразу после завершения триажа убрал бы отдельную границу включения следующего pipeline. Использование одних меток вместо принятого контракта потеряло бы саму оценку и сведения о ее происхождении.

### 2. Используем компактный граф

```text
триаж: неразрешенное воспроизведение дефекта -> запрос метки need reproduce
  -> принятый результат триажа в отдельно включаемый основной pipeline
  -> дефект с неразрешенным воспроизведением? -> глубокое воспроизведение [Tester]
       -> не удалось воспроизвести: метка + оставить открытым + завершить
       -> окружение недоступно / не хватает данных: пауза
       -> воспроизведен: продолжить
  -> крупный? -> подготовка OpenSpec [Analytic]
  -> фиксация спецификации или Accepted Work Contract
  -> приемка требований человеком по правилам компонента/размера/приоритета
  -> изолированное создание приемочных тестов [Tester]
  -> реализация / исправление [Coder]
  -> независимое ревью кода [Coder, отдельный запуск]
  -> прогон тестов [Tester] с доверенной валидацией и проверками репозитория
  -> Delivery [DevOps] -> доверенная публикация PR
  -> delivered_for_review + ссылка на PR

человек мержит PR на Git-хостинге, в том числе в production-ветку, вне этого pipeline

замечания ревью / падение тестов -> доработка в пределах лимита
                               -> ревью -> валидация
```

Для `large` используется OpenSpec; `small` и `medium` его пропускают. Так явно трактуется условие «не крупный». Ни один агент повторно не оценивает размер тикета. Один этап глубокого воспроизведения может выполнять нужные команды в пределах собственного бюджета; это не бесконечный цикл исследования. По умолчанию разрешен один дополнительный цикл доработки реализации; лимит настраивается при публикации. Единственная точка приемки человеком внутри pipeline — настроенная приемка требований. Merge PR остается ручной операцией на Git-хостинге. Нет отдельного AI-ревьюера спецификаций, приемки по оценкам модели или повторных узлов проверки готовности. Обычная проверка схемы результата и соблюдения контракта кандидата остается частью существующего завершения этапа.

### 3. Разделяем результат воспроизведения и доставку меток

Этот change расширяет настроенную политику отчетности пресета триажа после появления контракта из соседнего change. Сам триаж при принятии классификации запрашивает `need reproduce` для дефектов с `not_reproduced`, `unknown` и `needs_research`, даже если основной pipeline выключен или еще не принял тикет в работу. Основной pipeline эту метку не выставляет: он получает сохраненный результат триажа и затем снимает метку по результату глубокого воспроизведения. Состояние `needs_input` остается на паузе и не переходит в разработку. Уже воспроизведенные дефекты и новые функции пропускают глубокое воспроизведение. Следующий pipeline читает принятый результат, даже если выставленная триажом метка еще ожидает доставки.

Через существующий механизм research/command сохраняем симптом, окружение, точный объект проверки, выполненные проверки и результат. Завершенная проверка с отрицательным результатом выбирает терминальное состояние `cannot_reproduce`. Через существующие Reporter/outbox запрашиваем метку `can't reproduce`, удаление управляемой `need reproduce` и открытое состояние тикета. Успешное воспроизведение снимает `need reproduce` и продолжает работу. Технический сбой никогда не означает отрицательный результат воспроизведения. Посторонние метки сохраняются. При настройке сопоставляем указанные строки по умолчанию с существующими метками установленной интеграции; не создаем метки неявно. Завершенный вход следующего pipeline остается учтенным в дедупликации, поэтому очередной опрос его не перезапускает.

Рассмотренная альтернатива: трактовать неудачный запуск shell-команды как невозможность воспроизведения означало бы смешать недоступность выполнения с результатом проверки симптома.

### 4. Фиксируем требования до создания независимых тестов

Для крупных тикетов изолированный профиль запускает подготовку OpenSpec: создает proposal, delta-спецификации, design и tasks в принадлежащем запуску рабочем каталоге, проверяет их согласованность и фиксирует ChangeSet требований. На этом запуск автора заканчивается. Оркестратор отдельно запускает создание тестов и реализацию; он не просит skill подготовки proposal выполнять реализацию в рамках того же хода планирования. Итоговый кандидат включает эти файлы требований. Если требования позже корректируются, создается новый цикл через существующий механизм Workflow Cycle, а результаты зависимых тестов и ревью теряют применимость.

Для некрупных тикетов фиксируем Accepted Work Contract на основе явных требований тикета и триажа. Документ завершения триажа никогда не служит приемкой реализации. Если ожидаемое поведение не описано, работа приостанавливается до получения данных. Этот пресет не выбирает отдельного агента ревью спецификации; другие опубликованные Flow могут его сохранить. Общий контракт политики требований меняется явно, чтобы не нарушать текущую основную спецификацию молча.

Запуск автора тестов получает только выбранные требования и контекст базовой версии. Сохраняем его тесты через существующий механизм публикации защищенных тестов, затем демонстрируем ожидаемое падение на базовой версии. Ошибки тестового инструментария или настройки останавливают подготовку. Если критерии приемки уже выполнены, сохраняем результат «изменение не требуется» и завершаем работу без пустого PR с исправлением. Реализация получает общедоступное описание области тестирования и требования, но не защищенные тесты и не историю работы их автора. Тесты, доступные обычным разработчикам, остаются частью TDD при реализации; изоляция приемочных тестов не освобождает coding-агента от правил репозитория.

### 5. Проводим ревью и валидацию зафиксированного кандидата

Используем существующие доверенную фиксацию ChangeSet, планирование ревью и исполнители защищенных тестов. Один ревьюер видит кандидата и требования, но не историю работы coding-агента. Затем детерминированная валидация разворачивает того же кандидата и исходный защищенный набор тестов и запускает обязательные проверки репозитория. Успешное ревью не заменяет выполнение тестов. На доработку передаются только ограниченные замечания, не раскрывающие защищенные проверки. Любая доработка меняет кандидата и требует повторного ревью и валидации в пределах исходного бюджета. Дефекты требований или тестов приостанавливают работу до явного цикла исправления; агент реализации не может редактировать защищенный набор.

### 6. Публикуем принятого кандидата для ручного merge

Используем существующий протокол Delivery с Observe/Publish/Cancel и возможность публикации `octacity-github`. DevOps готовит метаданные PR и ограниченный план публикации на основе принятого кандидата и сводок ревью и валидации, затем через разрешенные доверенные инструменты публикует PR и наблюдает результат. AI-запуски не получают прямых учетных данных для записи на Git-хостинг. Доверенный адаптер публикует только принятого кандидата по существующей политике целевой ветки. Команда merge, учетные данные для merge и политика его выполнения не добавляются.

В существующем компоненте операций и хранения Delivery сохраняем исходный идентификатор публикации, точные репозиторий, базовую версию и кандидата, Decision и ссылку на PR. После неизвестного результата сначала наблюдаем состояние перед повторной попыткой, чтобы вернуть тот же PR после успешной удаленной публикации. Конфликт или сбой публикации остается видимым и не считается успешной доставкой. Кандидат на замену должен пройти ревью и валидацию до публикации.

Успешный Delivery заканчивается результатом `delivered_for_review`, URL PR и подтверждением публикации. Человек проверяет и мержит PR на Git-хостинге по правилам репозитория, в том числе для production-веток. Этот change не добавляет подтверждение merge внутри pipeline с последующим автоматическим выполнением и не требует мониторинга merge для завершения сценария. Публикация PR не должна отображаться как смерженный код или автоматически завершенная реализация тикета. Настроенная отчетность может отдельно отражать передачу на ревью.

### 7. Используем существующие настройку и отображение результатов

Расширяем общие механизмы обнаружения и разрешения пресетов, чтобы выбирать новый пресет, не создавая отдельное семейство endpoint. В настройке Console выбираются вход предшествующего триажа, роли, профили и входные данные каждого этапа, точные зависимости, программа воспроизведения, сопоставление меток, бюджеты, правила приемки требований, целевая ветка PR и конфигурация публикации. Один общий отчет готовности перечисляет недостающие возможности. Существующие экраны Run/Issue показывают условные ветки, выбранных агентов и безопасные сводки входных данных, ссылки на требования, общедоступное описание области тестирования, ревью, валидацию, PR и подтверждение публикации, а также разрешенные действия человека для приемки конкретной версии требований. Итоговый результат доставки содержит ссылку для ручного merge на Git-хостинге. Метаданные защищенного набора видны, его исходники — нет.

### 8. Отдельно задаем AI-роли и входные данные каждого этапа

Выбираем принадлежащие Project роли с именами `Tester`, `Coder`, `DevOps` и `Analytic` и фиксируем совместимый Profile для каждого этапа. Имена описывают ответственность, а конкретное выполнение выбирают явные неизменяемые привязки. Можно повторно использовать уже выбранные роли. Профили этапов могут отличаться runtime, моделью, инструкциями, инструментами и данными при общей роли. Реализация и ревью всегда выполняются в отдельных изолированных запусках, даже если выбран один Profile роли Coder.

| Этап | AI-роль | Входные данные и доступ конкретного этапа |
| --- | --- | --- |
| Глубокое воспроизведение | Tester | Симптомы из тикета, принятый триаж, нужное окружение и конфигурация; выбранные фрагменты исходников — только если нужны способу воспроизведения. |
| Требования и спецификации | Analytic | Тикет, триаж, правила Project, выбранные документы и конфигурация; фрагменты репозитория — только при явном выборе. |
| Создание приемочных тестов | Tester | Зафиксированные требования, контракты базовой версии/API, выбранные настройки тестирования и необязательные фрагменты исходников; будущая реализация и история ее создания недоступны. |
| Реализация и исправление | Coder | Принятые требования, разрешенный рабочий каталог исходников, выбранные конфигурации, общедоступные сводки воспроизведения и тестов; защищенные тесты и история их автора недоступны. |
| Независимое ревью | Coder | Конкретный кандидат/diff, принятые требования, выбранные исходники, конфигурация и общедоступные замечания; история реализации и защищенные проверки недоступны. |
| Прогон тестов и валидация | Tester | Идентификатор кандидата или endpoint, план тестирования, выбранное окружение, конфигурация и реальные отчеты выполнения. Доверенный исполнитель подключает защищенный набор и кандидата, необходимые способу тестирования; доступ AI к исходникам и набору задается отдельно и может отсутствовать при тестировании через внешний интерфейс. |
| Delivery | DevOps | Принятый кандидат, сводки ревью и валидации, политика PR и целевой ветки, нужная конфигурация и применимые подтверждения приемки требований; исходники не передаются, если не нужны и не выбраны явно. |

Таблица задает значения по умолчанию и допустимые входы, но не дает неявного доступа ко всем перечисленным данным. Для каждого этапа независимо настраиваем видимость исходников — без доступа, выбранные фрагменты конкретной ревизии или разрешенный рабочий каталог, — выбранные результаты предшественников и дополнительные артефакты или файлы конфигурации через `FlowContextBinding`, подключения файлов и права инструментов. Отсутствие обязательных входных данных блокирует только их потребителя. Зависимость по порядку выполнения или общая роль не передает все данные предшественников. Требования Profile к контексту должны соответствовать этим привязкам. Для каждого запуска сохраняем получившийся Context Manifest. Инструмент не может извлечь исключенные исходники или артефакты через более широкое, не объявленное подключение.

Прогон тестов, как и их создание, включает настоящий запуск AI-агента Tester. Он использует разрешенные инструменты выполнения, чтобы запустить или наблюдать подготовленный план и сформировать диагностику. Успех определяют исполняемые тесты и доверенные отчеты; текст агента не может превратить упавшие, пропущенные или не запущенные обязательные тесты в успешный результат. Инструменты используют обычное выполнение Build/Job и исполнитель защищенных тестов. Аналогично DevOps работает через доверенный механизм Delivery, не получая прямых учетных данных Git-хостинга и не публикуя изменения произвольными shell-командами.

Изоляция входит в результат реализации этого change: нужны ее настройка и поведенческая проверка через обычный путь выполнения. Одних Context Manifest и инструкций в prompt недостаточно для ограничения доступа. Права этапа должны применяться к файловой системе и подключенным каталогам, чтению артефактов, командам и дочерним процессам, сети и MCP-инструментам, привязкам учетных данных. Рабочий каталог, сессия, окружение и доступ к секретам другого запуска не наследуются. Если выбранная среда выполнения не может обеспечить нужное ограничение, запуск останавливается без перехода к более широким правам.

Analytic пишет только в разрешенные пути требований и выходных файлов; автор тестов — в свой рабочий каталог защищенных тестов; Coder реализации — в разрешенные пути реализации. Coder ревью читает выбранного кандидата, но не может его изменять. Прогон тестов использует изолированные временные и выходные каталоги без изменения сохраненного кандидата или защищенного набора. DevOps может запрашивать ограниченную доверенную публикацию PR, но не получает прямых учетных данных Git-хостинга или инструмента merge. Каждый этап может записывать явно разрешенные отчеты. Эти права задаются отдельно для этапов и не зависят от отображаемых названий ролей.

### 9. Настраиваем приемку требований человеком

Фиксируем правила приемки требований в неизменяемой политике пресета. Правила объединяют принадлежность компонента набору, размер из триажа и диапазоны приоритета из принятого результата триажа; важность задает поле `priority_assessment`. По результату выбирается приемка человеком или автоматическое продолжение. Правила применяются к созданной спецификации либо Accepted Work Contract некрупного тикета до создания тестов. Повторной оценки размера или приоритета нет. Человек видит тикет, нужные поля триажа и конкретную версию требований и design. Тикеты, не подошедшие под правила, продолжают выполняться автоматически. Приемка сохраняет пользователя, точный digest требований или контракта, политику и текущую попытку приемки. Отказ или запрос изменений останавливает продвижение и использует объявленный маршрут исправления; измененные требования требуют новой приемки и нового зависимого цикла тестов.

Используем существующие `HumanGate`, авторизацию оператора и журнал ответов. Для приемки требований подходит существующая привязка ответа эскалации (`Resume`/`Abort`) с представлением логического этапа требований. Расширяем текущие проекции только там, где не хватает привязки требований и приемки, не вводя отдельную подсистему согласований. Политики фиксируются при публикации и допуске запуска. Ожидающие запросы сохраняются при перезапуске и видны в Console и диагностике API. Агенты не могут подтверждать собственную приемку или обходить ее.

Отдельной приемки merge внутри этого pipeline нет: после публикации PR человек выполняет merge на Git-хостинге. Ревью и согласование изменений для production-веток регулируются существующим ручным процессом репозитория.

## Риски и компромиссы

- **Триаж реализуется параллельно.** Используем его принятый публичный результат и механизмы отчетности; задачи следующего pipeline и расширения меток оставляем здесь, не изменяя артефакты соседнего change.
- **Независимым защищенным тестам нужны исполнимые критерии приемки проекта.** Приостанавливаем подготовку, если нет ожидаемого поведения или окружения; не подтверждаем реализацию критериями завершения триажа.
- **Целевая ветка PR меняется во время работы.** Показываем конфликт публикации по существующей политике целевой ветки; новый кандидат должен повторить ревью и валидацию. Автоматическое разрешение конфликтов не входит в этот пресет.
- **Правила самого репозитория требуют ревью человека.** Оставляем это ревью и ручной merge на Git-хостинге; публикация не означает, что изменение смержено.
- **Публикация успешна, но ответ потерян.** Наблюдаем исходную стабильную операцию доставки и возвращаем тот же PR через существующий механизм восстановления.

## План перехода

Собираем вход следующего pipeline и пресет на существующих контрактах публикации и восстановления, затем расширяем обычные настройку и экраны. Публикуем новый пресет без изменения существующих неизменяемых конфигураций. Его вход и конфигурацию публикации PR включаем явно при настройке. Проверяем весь сценарий до `delivered_for_review` с герметичными фикстурами моделей и провайдеров и обычным путем выполнения Agent/Build. Реальная внешняя публикация выполняется только при отдельном включении.

Откат отключает прием новой работы и публикацию для будущих запусков. История уже допущенных запусков, PR и подтверждения публикации сохраняются. Отключение не закрывает существующие PR и не отменяет ручные изменения в репозитории.
