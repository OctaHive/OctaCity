## Context

See `proposal.md` for scope and motivation. Findings below describe the current worktree; independent uncommitted CI, document and criteria corrections are not implementation of this change.

Existing `server/dark-factory` requirements already demand generic configured logical stages, isolated Context and ordinary Builds. This change completes first-use authoring and explicitly revises the repository-only admission/Build assumptions in `server/project-runs` and REST. It supersedes the dedicated Console journey in the active triage change for future authoring, without rewriting that change's retained delivery evidence or completing sibling changes.

## Goals / Non-Goals

**Goals:** One common draft/validation/publication path; first-step choices from installed capabilities; explicit criteria/document/resource recipients; real repository-free execution and different repositories across steps; preserved exact provenance and recovery. The two-agent triage example is the acceptance workload authored by the operator, not a product template.

**Non-Goals:** A template marketplace, automatic planner, new graph interpreter, second Job executor, arbitrary executable gate scripts, new credential or document store, shared chat history, automatic capability installation, repository knowledge indexing, paid-model qualification, downstream ticket-delivery implementation, or unrelated redesign of task status workflows. Existing installed capability prerequisites remain explicit.

## Decisions

### 1. Keep one ordinary definition and execution path

Use the existing Flow Definition, Factory Configuration, Role/Profile, Context, Node Attempt and ordinary Build owners. In Console, Add pipeline is a coordinated visual graph editor for these resources, not another persisted pipeline/execution entity. Steps are graph nodes with configurable inspectors; operators create, connect and edit conditional transitions visually, with keyboard-accessible equivalents. Both visual and headless authoring produce the same validated Flow. Nested sub-Flows are outside scope. Make Flow versus Configuration publication and activation understandable within that journey while keeping their existing exact identities and headless commands.

Replace the hardcoded triage button and future-authoring dependency on the triage-shaped resolver only after common authoring reaches equivalent execution coverage. User-defined names and schemas must suffice. Renaming steps, adding a third step or removing classification must not need a special API or Rust stage registration. Retained old Flow definitions remain readable and executable. Released example configuration may remain in tests or the explicitly requested development stand; it cannot seed the clean-system acceptance path.

**Alternative considered:** Rebrand the current triage wizard or add more business wizards. This leaves the first-step binding problem and business-specific state in authoring, so it does not satisfy the acceptance boundary.

### 2. Resolve bindings from existing installation facts

Extend/generalize Project-visible capability choices and shared read-only draft validation. Extract compiler-derived Build binding selection from the current preset assembly owner; do not copy it into the frontend. Resolve exact Role/Profile, tool/plugin/model, supported source mode, result/evidence contract and permitted Build Configuration references using current installation facts. Keep startup independent of live model discovery.

Expose installed gate/action parameter and result contracts through the same typed choice mechanism. The constructor authors bounded schemas, comparisons, boolean/array predicates, outcomes, projections and effects. Audit the existing assessment/classification assembly for hidden mandatory aliases or business codecs; replace dependencies in the manual path with ordinary configured data and existing technical evidence verifiers. Preserve native evidence provenance and fail-closed acceptance. A generic result editor is not permission to trust a model's `verified` flag.

Existing Flows can remain copy sources as an optional convenience. No catalog, installed binding or initial empty graph may depend on them. No second plugin registry, provider query wrapper or resolver persistence is introduced.

Separate reusable agent definition from its current assignment. Role/Profile owns general capability descriptions, working methods, skills and execution settings; the Flow node owns editable step instructions, expected result schema and configured checks/routes. Project-fit and duplicate assessment and stage-specific result examples belong to that node's reviewed assignment/contracts, not to a mandatory triage Role/Profile or technical runtime. Project component/priority vocabularies and their meanings come from explicitly attached Project documents rather than required duplicate step lists. A skill may teach a reusable method but does not automatically assign it to every invocation. The same exact Role/Profile must support two differently tasked steps without cloning or editing the agent.

Freeze the step assignment and its digest through existing versioned Flow/managed-input and invocation package owners. Compile it as an explicit reviewed instruction layer distinct from reusable agent instructions and from untrusted Issue text, reference documents and accepted predecessor data; do not implement this by placing arbitrary data into an input labeled as instructions or allowing data to override policy. Preserve controlling Project policy and permission ceilings. Retrying or restarting an accepted Run retains its original step assignment; editing an assignment publishes a new Flow version without changing the Role/Profile or sibling nodes. Add only the explicit compatible contract needed in ordinary node/task intent, with legacy canonical encodings/replay preserved and no second prompt journal. Existing immutable specialized profiles remain readable/executable; the new manual journey and stand example must demonstrate reusable agents with step-owned tasks rather than rewriting old versions.

Agent step inspectors group role and profile controls in a distinct Executor section, separate from Documents and other input attachments. Label Role and Profile explicitly, show current exact selections/versions and distinguish browsing a role's profiles from assigning a profile. Reuse the existing Role/Profile owners, selection policies and authoritative compatibility checks; do not introduce another executor identity or infer selection from a step/role display name. A changed role must not silently retain a profile from the previous role. Preserve independently selected documents and report any newly unmet Profile context requirements without automatically attaching or removing content. Browsing or selecting an executor only changes the in-memory draft and never starts a Job. Installed runtime management remains contextual navigation rather than an unlabeled substitute for selecting the executor.

After profile selection, Executor shows a readable summary of the selected version's runtime/model settings, instructions and skills where supplied by the existing authorized profile/role contracts, plus a View profile link opening that exact version while preserving the in-memory pipeline draft. Use retained structured settings rather than an inferred or model-generated summary; distinguish unavailable settings from an explicitly empty value. Viewing does not replace the selected version or mutate the profile. Private instructions remain subject to current authorization and existing no-persistence rules.

Place MCP connections in a separate Tools and access section of the same step, showing understandable connection/resource names, configured scope and safe missing/incompatible reasons. Do not place credential plumbing directly below the profile choice. Technical configuration/resource identities, digests and logical credential/secret references belong under a keyboard-accessible Details disclosure; secret values are never displayed or resolved for this view. The selected profile still owns its immutable declared bindings, and this layout introduces no alternate permission or credential owner. Show configured access separately from any existing verification evidence; catalog metadata must not look like a successful authenticated call, and opening the section must not probe a peer or execute a tool.

### 3. Separate Project documents, pipeline criteria and step inputs

Move shared document browsing/viewing/editing to Project settings using the current Project input APIs, authorization and content reader. Retain immutable Artifacts and exact references. Publishing an edit creates a new content identity; do not invent a mutable document owner or silently reinterpret same-name publications as one version chain. Show available exact publications/history with their existing metadata.

Each step inspector has one Documents list with bounded multiple selection from authorized Project documents, exact-version read-only preview and removal. Do not split it into Goals, Rules and Additional documents fields or require manual technical aliases to attach ordinary documents. Existing logical keys remain in the ordinary typed Context bindings. For each selected document, show and explicitly select agent instructions or reference material; neither its name nor its prose determines that role. Compile these roles to existing Policy versus Specification Context semantics. Selected controlling policy retains its existing instruction precedence and cannot grant tools, credentials or execution permissions. Keep any independently required Project policy applicable; generic document selection cannot waive it. An empty list is supported unless explicit selected Profile/input requirements need a document, with an actionable prerequisite rather than a fixed business slot. Document opening, publication and attachment remain distinct. Replace the ambiguous None picker with a labeled unselected state and an explicit create action in Project settings. Open the shared document area alongside the active editor, preserving its existing component-memory draft; do not persist draft text in browser storage to implement navigation.

Pipeline goals and completion criteria belong to the common definition draft and have an explicit editor and recipient selection. They describe the purpose and completion of this process, separately from Project goals; each step separately defines its result schema, and an Issue's implementation acceptance remains original task data. Freeze this content through the existing immutable definition/managed-input publication contracts at explicit confirmation. Reuse current idempotency and preparation/recovery handling for publication failures rather than create a criteria journal. Referenced Project content requires explicit new selection; editing inline pipeline goals/criteria does not mutate that document.

**Alternative considered:** Keep a full document-management form inside every pipeline or step. Reusing Project management plus selection avoids duplicate editors and ambiguous attachment side effects.

For classification, Project documents are the source of component descriptions and priority scales/meanings. The step task explicitly tells the agent how to use those selected documents and preserve uncertainty. The constructor must accept bounded result fields/types without requiring the operator to copy document values into enums or a second vocabulary registry. Generic enum schemas remain an optional technical facility, not a prerequisite for this journey. Retain exact document versions through the existing Context owner; later publication does not repin accepted Runs. Schema-valid output establishes structure only, not semantic adherence to prose; any stronger validation/acceptance requires an explicitly configured check or review. Missing/ambiguous guidance follows the declared uncertainty/review route rather than an invented default. Assessment priority remains separate from admitted queue/Issue planning priority unless a distinct authorized action explicitly changes a supported field.

Reporter configuration remains separate and uses ordinary action nodes, conditions and accepted-result projections with an explicit Source/Reporter target and current write grant. Allow independently reviewed add/remove-label and preserve/change-state effects: adding a label must not imply closing a ticket. For document-guided scalar results, support bounded literal predicates and declared no-effect/review fallback without requiring a complete enum copied from the document; reuse the existing generic predicate/action machinery. Only configured permitted provider literals may be written. Agent output or document prose never becomes a dynamic provider label, resource target or close command, and an unmatched value must not trigger an inferred write. Preserve current delivery receipts, retries and effect ownership rather than add another Reporter state owner.

### 4. Separate the admitted subject from each step's code resource

Declare the pipeline's available code sources in the existing versioned Flow/Configuration authoring aggregate as references to authorized Project repositories, with declared revision-selection rules and access/scope ceilings. This is configuration, not a new repository registry or source state owner. Pipeline availability never mounts, checks out or exposes a source to any step. A step independently selects no code or one primary source from that declaration, an exact revision or accepted candidate bound to it, supported access mode and optional bounded path/range scope. Selection can narrow but never widen the declared ceiling or current effective policy. Different steps can select different sources; multiple writable repositories within one step are not required here. An empty source declaration supports repository-free workflows. Reject undeclared source references and removal of a declaration still used by a step until that step is explicitly reconciled; do not silently detach or remap it. Published replacements preserve admitted Runs and their exact bindings while current authorization remains enforced.

Introduce a versioned typed repository-free Project/input subject in the existing Work/task contracts, alongside the legacy exact repository subject. It retains Work/Project ownership and immutable admitted input provenance without a fake repository.

Retain the original Work correlation and the exact node/attempt resource identity together. Replace unconditional equality to Work's repository subject with validation of the declared immutable per-step binding and its admitted scope; never relax it to 'same Project is enough'. Candidate, evidence, artifact and handoff validators must reject subject substitution, cross-repository candidate reuse and a changed resource set. Mutable refs are resolved/frozen before dependent protected I/O/dispatch; retries and restart reuse those pins.

A default Work subject is metadata, not permission or implicit attachment. No-code steps must make no VCS request and have no code checkout or inherited repository mount. Repository paths, credentials, read/write modes and network remain independently narrowed by Project, Configuration, Profile, installation and Agent/backend policy. A factory selection cannot widen an ordinary Build Configuration's source or permission ceiling; incompatible technical bindings block validation/readiness.

### 5. Support no-code execution through ordinary Builds

The current ordinary Build contract requires Repository/revision, so repository-free Work is insufficient by itself. Add explicit versioned source-free ordinary Build/Job intent and qualified executor support. Preserve the existing repository-backed form and its canonical bytes, digests, replay and source-resolution semantics. Source-free intent omits checkout through validated ordinary source policy, not through an empty repository URL, synthetic revision, hidden bootstrap checkout or alternate runner.

Carry the source mode through immutable Build input, signed JobSpec intent, placement capability checks, materialization, output provenance, retry and diagnostics. Unsupported Agents/protocols/backends reject it before leasing/spawn with an actionable reason. Reasoning still runs as an ordinary isolated Job with a private execution workspace and separately selected credentials. Existing ordinary CI/CD remains repository-backed unless explicitly configured otherwise; its Trigger, Attempt, Job and result behavior must remain unchanged.

**Alternative considered:** Treat the pipeline's available source declaration as a mandatory checkout for every step and merely hide files from one prompt. That retains unwanted VCS/checkout dependencies and cannot execute document-only workflows. Declaring availability and explicitly attaching code are separate operations.

### 6. Treat publication and recovery as existing multi-resource operations

Replace the combined Root execution and Configuration limits form with three pipeline sections. Start and queue explains admission and concurrency, distinguishing concurrent Runs, configuration-wide active nodes and nodes within one Run. Execution limits provides the run budget and explains attempts, time, tokens, cost and output with human-readable units; step budgets stay in step inspectors. Pipeline access presents the overall permission ceiling and requested graph access, separately from actual step attachments in Tools and access. Declaring a pipeline ceiling never grants that access to every node.

Use shared authoritative normalized validation to return each effective bound/access scope and its applicable sources: Project policy, Factory Configuration, Flow, selected step/Profile and qualified runtime enforcement where relevant. Present the limiting source and a readable explanation; keep exact policy/version references under Details. Values not yet resolved or enforceable remain explicit blockers rather than invented effective settings. Draft choices do not prove dispatch-time authorization; publication/dispatch still revalidate through existing owners. Keep budget aggregation and retry bounds intact: a per-step ceiling, a whole-Run allowance and a configuration-wide concurrency bound are different scopes, not interchangeable numbers to collapse into one minimum.

Avoid independent duplicate editors for equivalent operator intent. Show inherited ceilings read-only with their source and authorized navigation; retain separately editable controls only for genuinely distinct scopes with clear labels and descriptions. Map intent to existing Flow/Configuration fields through shared normalization, not frontend-derived authority or another policy store. If a request exceeds an enclosing bound, show the requested value, applicable maximum and owning source, preserve the draft and require explicit correction rather than silently raising/clamping policy. This presentation must leave existing wire forms, signed intent, enforcement and admitted Run versions unchanged in meaning.

Shared validation stays read-only and never probes providers or resolves secret values. Review names exact definitions, criteria, documents, resources, permission narrowing, schemas, routes, budgets and effect mappings. Confirmed publication uses existing immutable commands and replay identities; Flow/Configuration/criteria/input publication can be sequential and must expose partial completion rather than claim one atomic operation. Source preview, canonical Issue import, intake activation, model access and Reporter authority stay independent.

No control edge, shared Role name, identical model or previous attempt grants context. Construct and retain separate execution packages/Context Manifests for each invocation. Only explicit accepted-result projections reach successors; no private investigation, raw transcript, unselected document/repository, protected test or credential is inherited.

### 7. Use clean-state execution as the release gate

Initial state has no Factory Flow/Configuration, copied business node, business preset or demonstration Work/Run. Operator-installed technical runtimes, ordinary worker Build capabilities, scoped connections, Agent/backend and generic verifiers are allowed prerequisites and must be enumerated in evidence. No fixture may install triage instructions, schemas, gates or bindings before UI authoring.

Through EN/RU keyboard/narrow UI, create Project documents and custom Role/Profiles, open an empty pipeline, add the two reasoning steps and gates, edit criteria, select recipients/resources and explicitly connect accepted outputs. Configure manual intake and a separately tested optional Source/Reporter input. Use real management routes, persistence and qualified isolated execution; finite model/MCP/provider peers supply protocol-correct outcomes, not handler substitutions or authority bypasses.

Also run an unrelated three-step workflow, a repository-free workflow, and a two-repository workflow. Restart after accepted stage output, change Project documents, revoke scope and lose publication/reporting replies. Verify original identities, bounded recovery, exact retained content and one logical effect. UI-only graphs, static JSON fixtures and metadata readiness do not establish executable completion.

## Risks / Trade-offs

- **Subject changes expand beyond UI** → Explicitly cover ordinary Build/protocol, store, signed intent and consumer compatibility; do not mark no-code support complete from a hidden selector.
- **Generality weakens evidence validation** → Keep technical proof/capture adapters, exact schema/subject checks and negative forged-evidence cases; configure business routing without trusting model-authored evidence metadata.
- **New wire forms change legacy hashes** → Use explicit new versions/forms, keep legacy serializers/readers and canonical replay fixtures, and test actual PostgreSQL restart parity before migration.
- **A new editor hides installation gaps** → Derive choices from installed qualified capabilities and expose actionable reasons; do not auto-install runtimes, copy credentials or broaden policy.
- **Document management navigation loses drafts** → Reuse the shared Project UI alongside the active in-memory editor and preserve explicit selections; no browser-persisted private drafts.
- **Further screen review adds scope** → This is an initial planning snapshot. Update proposal/specs/design/tasks together as findings are accepted, before starting apply; no claim that the rest of the screen is reviewed.

## Migration Plan

1. Start with the first behavior's focused Red/Green slice, not a repository-wide baseline gate. Before refactoring a boundary, run its affected existing behavioral tests and add characterization only where relevant coverage is missing. Keep compatibility checks with the slices that change those contracts; run the broader matrix at final qualification without repeating unchanged successful checks. Monitor disk during build-heavy work and keep unrelated worktree fixes separate.
2. Add compatible readers/contracts and additive, reentrant persistence changes for source-free subjects and per-step resources; keep legacy values and history untouched. Upgrade protocol consumers/capability advertisement before enabling new forms.
3. Deliver shared authoring, Project documents/criteria and per-step inspector controls in TDD slices. Keep intake disabled until ordinary explicit activation.
4. Prove the complete clean-state journey. Then remove the dedicated triage UI and hardcoded new-authoring dependency; retain saved Flow inspection/execution. Document retired authoring operations and generated-client migration explicitly; do not silently reinterpret their bodies.
5. Adapt the explicitly requested `tools/factory-stand` development example to publish ordinary definitions through the same common path; it must not become an acceptance prerequisite. Share resulting contracts with sibling planned changes without implementing their business workflows.
6. Rollback disables new intake and returns future authoring to the prior supported deployment. Never downgrade a reader while new subject/protocol forms remain active; retain capable workers/readers for admitted Runs or restore a consistent verified backup. Do not delete new history, rewrite subjects or reset the stand to claim rollback.
