# Task 2.8 verification

## Scope and public boundaries

The Console exposes manual Project task list/create and a URL-addressable base
Issue card, independently of integrations, repositories and Factory setup.
`Project > Tasks` uses the existing Console shell and Project navigation. The
card keeps its human key/title, pinned business status and explicit unavailable
pipeline-start affordance in a stable compact header. Overview is the default;
requirements and a bounded Activity preview sit beside basic Properties on the
desktop. Narrow Properties supports keyboard focus, viewport navigation and
return to its trigger. Technical identity/timestamps are progressive Details.

The public test seams are rendered Console routes and browser journeys through
the existing generated REST client. They cover manual creation, full-content
review/edit, exact revisions, direct organizational moves, status history and
explicit workflow adoption. No executor, provider effect, Factory control or
mutable Work is introduced. Expanded properties remain task 2.12, while execution
start/results belong to the later execution-request tasks, including 3.5. Those
unavailable sections state availability rather than fabricate execution facts.

Shared workflow transport moved unchanged from feature internals to
`ui/src/api/issueWorkflows.ts` so both workspaces can use it without forbidden
feature coupling. Existing workflow behavioral tests passed before and after
this move. Query keys remain centralized; selectors reuse `SelectMenu`.

Generated OpenAPI bounds drive UTF-8 validation, priority bounds and Issue page
size. Dedicated task/revision/history/choice query bodies have zero inactive
cache lifetime. Drafts and frozen confirmed requests stay in component memory;
only safe section/revision selection enters URLs. Generic notifications use
command labels, excluding requirements and reasons. Provider and repository
configuration are absent from the manual form.
