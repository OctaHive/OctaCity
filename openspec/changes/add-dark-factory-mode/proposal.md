## Why

OctaCity already provides a durable CI/CD execution substrate and Octa now has an official Codex task plugin, but there is no durable programmable work lifecycle that can compose ticket triage, requirements, test-first development, independent verification, promotion, and bounded feedback across multiple isolated calls and Builds. Adding a deterministic nested-flow runtime turns the existing execution platform into an opt-in dark factory without making ordinary CI/CD depend on an LLM or replacing the established Build, Agent, and Octa contracts.

## What Changes

- Add an opt-in Dark Factory mode alongside the existing standalone CI/CD mode; ordinary Triggers, Builds, Attempts, Jobs, and Results continue to work without a Factory Configuration, model provider, or coding harness.
- Add provider-neutral Work Envelopes, versioned Factory Configurations, durable Factory Runs, append-only attempts, bounded budgets, WIP limits, phase-ready pools, fencing, cancellation, retry, escalation, and restart reconciliation above ordinary immutable Builds.
- Add immutable versioned Flow Definitions and nested Flow Runs whose closed execution primitives invoke an ordinary command/Build, a bounded reasoning harness such as Codex, or a provider-neutral Decision Signal such as JEV or a future Decisions API. Deterministic gate, fan-out/join, human-approval, trusted-action, and subflow nodes own control without allowing provider-authored stages or transitions.
- Define triage, research, requirements and subsequent logical stages as supplied immutable node/flow configurations, including prompts/profiles, bounded data schemas, input projections, gate predicates, outcome mappings and transitions. Use one node execution contract, retained-result journal and ordinary Build adapter; Factory runtime and persistence SHALL NOT require stage-specific types or dispatch paths when an operator adds a logical step.
- Implement canonical Factory Flow structure and validation as a pure internal OctaCity module, record the semantic matrix against Octa task DAGs and the existing OctaCity Job DAG, and defer any shared graph-kernel extraction until working consumers prove a stable common seam; Octa in-process execution and OctaCity durable fenced interpretation remain separate in every case.
- Separate control dependencies from Context Manifest dependencies so a node may wait for another node without seeing its inputs or outputs, while explicitly selected typed handoffs, summaries, Artifacts, source ranges, skills, and configuration documents can be passed to declared successors.
- Support configurable two-phase triage, optional defect or feature research, requirements, test-first development, independent review, verification, deployment, and post-deployment observation flows as compositions of the same primitives. Triage records Work kind, duplicate and Project-fit eligibility, classification, preliminary reproducibility, and a finite next route. Small work may bypass specification authoring through an exact Accepted Work Contract but still follows its declared test and implementation gates, while a typed requirements defect creates a new append-only requirements cycle and invalidates downstream authority without deleting history.
- Adopt the official Octa Codex plugin in the pinned OctaCity release path and compile an immutable Factory Task Envelope into a normal Octa task while keeping Codex semantics out of the Agent and server protocols.
- Add deny-by-default Factory Permission Sets that intersect Factory policy, immutable task intent, local Agent grants, and backend capabilities for plugins, tools, commands and arguments, filesystem roots and mounts, network hosts, secret and workload-identity profiles, descendants, resources, and outputs.
- Add trusted ChangeSet capture and lineage for exact specification, hidden-test, implementation, and rework candidates; deterministic validation and evidence production; read-only evaluator connectors; versioned criterion packs; immutable assessments; and a deterministic Decision Engine. Program code owns loops, branches, joins, retries, budgets, and stop conditions; model calls return bounded typed values and never authorize lifecycle transitions.
- Add protected hidden-test authoring and validation so implementation calls can be ordered after test creation without receiving test source, author transcripts, or hidden assertions. Independent verification can similarly receive only the exact deployable Artifact, public contracts, selected evidence, and environment authority declared by its flow node.
- Add a provider-neutral Decision Signal boundary for optional probability-backed routing and tool-risk assessment. JEV is the first adapter; later decision-model or Decisions API adapters can be selected through immutable capability-based configuration without changing factory domain types. Signals may choose only among predeclared routes or narrow an already-authorized tool action, and deterministic policy remains authoritative.
- Add write-capable delivery and promotion boundaries that can idempotently publish an accepted candidate, create or update a review target, and invoke or observe existing CI/CD deployment pipelines without giving reasoning Jobs forge or production credentials. Immutable flow policy may select declared stage-only, staged approval, canary, A/B, progressive, or immediate low-risk routes with bounded observations and failure paths; no model can merge or deploy directly.
- Add complete REST and Operator Console management workflows for guided Factory Configuration and typed Flow Definition graph authoring, immutable-version publication, manual Work admission, phase-ready pools, nested Flow Runs, nodes, cycles, candidates, evaluation, decision, escalation, delivery, and promotion inspection and commands; every workflow remains available headlessly through REST.
- Preserve exact revision, generic Artifact/report, audit, retention, visibility, idempotency, optimistic concurrency, secret-redaction, and same-origin trusted-network contracts.
- Keep external ticket polling/webhooks, concrete GitHub/GitLab Work Source and Work Reporter adapters, and an Octa-local JEV task plugin outside the initial manual-intake slice; the provider-neutral source/reporting and Decision Signal boundaries remain ready for separately scoped follow-up changes.
- Keep unconditional automatic merge or production deployment, dynamic infrastructure provisioning, arbitrary repository-authored workflows, provider-authored control flow, unbounded recursion, and a universal coding-plugin abstraction outside the initial release. Policy-authorized promotion is allowed only through declared trusted nodes after every required gate.

## Capabilities

### New Capabilities

- `server/dark-factory`: Provider-neutral work admission, immutable nested Flow Definitions, durable Factory Run coordination, code-owned agentic workflow, optional typed Decision Signals, Codex execution, candidate lineage, protected tests, evaluation, deterministic decisions, bounded correction cycles, verification, delivery, and promotion.

### Modified Capabilities

- `server/project-runs`: Preserve the independent CI/CD lifecycle while allowing a Build-backed Node Attempt to create an ordinary immutable Build with exact factory causality and narrowed effective policy.
- `server/agent-scheduling`: Extend placement and pre-spawn enforcement with the typed Factory Permission Set and fail closed when a requested restriction cannot be enforced.
- `server/vcs-integration`: Add a protocol-separated, write-capable and idempotent delivery adapter for accepted exact candidates while keeping ordinary VCS access read-only.
- `server/operations`: Recover and reconcile Factory Runs after restart and include factory transitions, evidence, decisions, and delivery in audit, observability, backup, and shutdown contracts.
- `server/rest-control-plane`: Add authorization-safe, bounded, idempotent Factory Configuration and Factory Run management and diagnostics without making the UI mandatory.
- `ui/operator-console`: Add a Dark Factory activity and contextual explorer for nested flows, node attempts, workflow cycles, phase-ready pools, candidates, evaluations, decisions, escalations, delivery, and promotion while preserving existing CI/CD activities.

## Impact

- Adds factory domain/application modules, store ports, PostgreSQL migrations and workers above the current Build application; existing Build orchestration, placement, and execution remain the only Job execution path. The initial configurable journey includes typed eligibility and classification triage, defect and feature research, Accepted Work Contracts, protected test authoring, implementation deliverables, and explicit rollout observations.
- Extends signed execution intent and Agent admission with factory permissions, and updates the pinned Octa release/local-stand inputs to include `octa_plugin_codex` and its verified distribution metadata.
- Adds Work Source, Decision Signal, evaluator, delivery, and deployment-observation boundaries plus initial manual intake, JEV, Codex, evaluator, and pull-request implementations. Provider SDKs and wire types stay in infrastructure adapters; a future Decisions API implementation plugs into the same Decision Signal contract.
- Extends the factory domain, persistence, REST, and console with immutable nested flow definitions and runs, typed node results, context projections, phase-ready pools, cycle and candidate lineage, hidden-test references, verification plans, and promotion observations.
- Adds one pure internal Factory graph module and a domain-specific adapter without adding an Octa graph dependency; it does not make the server depend on the Octa executor, plugin manager, process runtime, or in-memory scheduler, and it does not move Factory persistence or transition authority into Octa. A shared kernel, if later justified by working consumers, requires a separately reviewed follow-up change and release.
- Adds REST/OpenAPI resources and an optional Operator Console management surface with typed configuration forms, generated client types, release documentation, security contracts, and released-product vertical slices; the console remains replaceable because every operation is available through REST.
- Introduces no breaking change to ordinary CI/CD API behavior; factory resources and routes are additive and opt-in.
