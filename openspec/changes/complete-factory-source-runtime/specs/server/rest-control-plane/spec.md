## ADDED Requirements

### Requirement: Released automatic-input management is operationally complete
When automatic intake is installed, the released server SHALL compose protected input/group discovery, exact-version reads, choices, validation, immutable publication, read-only preview, retained dependencies and Source/Reporter diagnostics over the same authoritative stores and compatible installed selections used by execution. Valid requests SHALL NOT fail because an advertised handler was omitted. Empty history SHALL return a bounded successful empty collection. Missing installation, incompatible profile, denied grant, stale version and provider outage SHALL retain distinct safe outcomes. Source support SHALL remain optional for manual Issues and manual Factory admission.

#### Scenario: Granted integration is selected in a pipeline
- **WHEN** an authorized operator opens automatic-input settings for a visible Factory Configuration and a currently granted resource with compatible installed Source/preparation support
- **THEN** the API supplies authorized choices/current inputs and accepts an explicitly confirmed versioned publication without repeated credential entry or an inferred import/default-selection change

#### Scenario: No input has used the connection
- **WHEN** a visible Project has no matching current inputs or retained dependencies
- **THEN** its bounded history/list request returns an empty successful page rather than an unavailable-handler error

#### Scenario: Source support or authority is missing
- **WHEN** a request depends on an uninstalled capability or resource outside the current Project grant
- **THEN** a safe capability/authorization result is returned before provider invocation without disclosing hidden resources or private configuration

#### Scenario: Publication response is lost
- **WHEN** input/group publication commits and the client retries the frozen intent/key after losing its response
- **THEN** the original version is returned without duplicate worker activation or admission

### Requirement: Released Project source controls reach existing Issue consumers
The protected API SHALL allow a permitted operator to discover compatible Source choices, preview bounded native candidates and explicitly review import activation or import for a Project before an internal Issue exists, without requiring a Factory target or code Repository. Import/refresh SHALL use the existing canonical Issue and observation contracts, current grants and bounded durable ownership. Current versions, enable/disable intent and replay SHALL remain explicit. Existing per-Issue attachment, mapping, pull, synchronization and conflict-resolution operations SHALL be composed against compatible installed profiles. Source credentials, URLs, private paths or opaque fabricated task identities SHALL NOT substitute for authorized choices. Import activation, execution-input activation and field/status synchronization SHALL retain independent intent and authority.

#### Scenario: Project has a Source but no Factory Configuration
- **WHEN** a permitted operator previews and explicitly enables its compatible installed Source import
- **THEN** the API retains the reviewed control and imports the canonical visible Issue under existing creation rules without a Factory Configuration, execution profile, Work or Run

#### Scenario: Concurrent requests import the same native task
- **WHEN** authorized imports in one Project/security partition observe the same installed native resource/item
- **THEN** they resolve one canonical Issue and retain their replay/provenance without merging unrelated tasks or disclosing a hidden canonical Issue

#### Scenario: Workflow default changes after import
- **WHEN** another workflow version becomes the Project default after an Issue was imported
- **THEN** subsequent source/mapping operations retain that Issue's existing workflow pin until explicit adoption and reject stale or incompatible review without silently migrating it

#### Scenario: Import or pull is disabled
- **WHEN** an operator disables Project import discovery or a retained link's pull through the appropriate current reviewed control
- **THEN** subsequent reads obey that control's scope without deleting task/history, enabling execution or substituting another credential

### Requirement: Runtime diagnostics distinguish configuration from intake progress
Diagnostics SHALL distinguish installed support, current read/write grants, import/input activation, supervised consumer availability, observation/import disposition, canonical Issue, admitted Work/Run and external delivery. Configuration/read checks and previews SHALL NOT be evidence of import, execution or successful reporting. Safe classified reasons and request correlation SHALL identify a relevant next action without private paths, raw provider responses, credential values or task bodies. Runtime faults SHALL remain scoped to affected consumers/inputs/effects.

#### Scenario: Provider is throttled after activation
- **WHEN** an enabled Issue consumer or execution input receives bounded provider retry advice
- **THEN** diagnostics report its deferred progress while retained Issues/results and manual readiness remain available

#### Scenario: Local status commits while reporting is pending
- **WHEN** an accepted configured Issue transition or Work-backed action queues an external update that has not completed
- **THEN** diagnostics retain the exact authorized subject/mapping/source correlation and pending/conflicting/exhausted delivery separately from the accepted local status and execution result
