## ADDED Requirements

### Requirement: Managed automatic inputs run through released Source and Reporter composition
The released runtime SHALL resolve explicitly enabled managed input/group versions through compatible installed Source, preparation and optional Reporter profiles and current connection/resource/Project grants. Saving a connection, granting a Project, checking access or previewing SHALL NOT activate import, execution or synchronization. Valid enabled execution inputs SHALL be discovered without restart and polled through the existing bounded supervised lifecycle. Disabling an input or revoking read authority SHALL prevent subsequent protected dispatch without rewriting accepted history. Open provider identities and exact native pins SHALL be retained, with GitHub as the concrete supported adapter and a synthetic provider qualifying the common boundary. Execution-only/no-card and read-only/no-Reporter intake SHALL remain valid.

#### Scenario: Operator enables a valid read-only execution input
- **WHEN** an explicitly published enabled input has compatible Source/preparation settings and current task-read authority but no Reporter or Issue-import selection
- **THEN** normal startup polls it and retains and admits its bounded mapped snapshot through ordinary Factory admission without native writes or a required internal Issue

#### Scenario: Existing source is granted to another Project
- **WHEN** an installed compatible resource receives a new Project grant and explicit valid import/input configuration
- **THEN** the running server resolves that Project's permitted consumer/profile/target without borrowing another grant, hardcoded IDs or a per-input image rebuild

#### Scenario: Preview and publication use the same profile
- **WHEN** a permitted operator previews a selector and publishes its execution input against current versions
- **THEN** dispatch uses the retained predicate/preparation choices under current authority while preview has created no authoritative import, progress, reservation, Work or Run

### Requirement: Released Issue consumers reuse independent Source observations
Normal released startup SHALL install compatible authorized observation and Issue import/refresh consumers independently of optional Factory execution. Explicit Project import SHALL reuse canonical Project/security/installation/native-resource/item identity and ordinary Issue creation, with bounded source text, no invented acceptance and the current default workflow's initial status. Concurrent/repeated imports SHALL resolve the same Issue without another logical creation or Run. Native status SHALL not select a local business status without a separately reviewed supported mapping and guarded transition. Retained-link refresh SHALL respect current read grants, independent pull control, field ownership and reconciled freshness even when the item no longer matches an execution selector. Import, refresh or source echo SHALL NOT implicitly enable execution or push.

#### Scenario: External task is imported without execution
- **WHEN** a Source-only Project explicitly enables authorized import with no Factory Configuration or writer
- **THEN** its native task becomes one visible linked Issue with ordinary initial workflow pin and no Work/Run or external mutation

#### Scenario: Execution is admitted before canonical import
- **WHEN** a native task already has input-scoped Work/Run and is later explicitly imported into its Project/security partition
- **THEN** canonical import and existing association recovery retain one Issue and the original admitted identities/snapshots rather than creating an Issue per Run or readmitting the work

#### Scenario: Linked task no longer matches an execution input
- **WHEN** an authorized retained-link refresh remains enabled after the task stops matching or the execution input is disabled
- **THEN** supported fresh source-owned fields can refresh under the existing mapping without another execution, while uncertain/stale/unchanged observations preserve existing revision rules

### Requirement: Released source recovery preserves canonical tasks and both reporting producers
The composed runtime SHALL reuse canonical Issue import/association, durable bounded observation/scan progress, preparation/admission replay and independently fenced ordered reporting. Restart SHALL preserve original Issue, input-scoped Work/Run and immutable inputs. Missing required Factory input content SHALL remain a classified disposition; an ordinary imported task draft SHALL need no fabricated execution acceptance. Optional reporting SHALL support both accepted Issue-status push intents and accepted configured Work-backed actions under their separately reviewed exact native target, mapping, provenance, current task-update grant and original deadline. Conflicting overlapping producers SHALL be rejected rather than double-enqueued. Neither source text, echo, workflow publication, Run completion nor later attachment SHALL authorize a write.

#### Scenario: Restart follows import or admission before progress completion
- **WHEN** the server stops after canonical Issue creation or Work admission but before acknowledgement/page completion
- **THEN** recovery reuses original identities and retained snapshots, completes pending association under existing policy and processes remaining candidates without duplicate tasks or executions

#### Scenario: Manual local status is pushed without a Run
- **WHEN** an authorized manual transition commits under an exact reviewed OctaCity-owned status push mapping with compatible installed writer support
- **THEN** the existing Issue projection delivers only its permitted native label/state effects without requiring Work/Run and preserves unrelated labels and the accepted local status

#### Scenario: Two producers overlap on a native managed field
- **WHEN** an Issue push and configured Work-backed source-update action would both produce the same business decision's overlapping native effects
- **THEN** existing producer validation rejects the conflict rather than sending duplicate or contradictory updates

#### Scenario: Either Reporter loses an update response
- **WHEN** the provider applied an accepted Issue- or Work-backed effect but its response was lost
- **THEN** bounded recovery observes before another uncertain write and converges the original ordered effect without a new logical action, Run or renewed deadline

#### Scenario: Read or write access is revoked
- **WHEN** a connection is disabled or the relevant Project purpose is revoked before a subsequent consumer/Reporter dispatch
- **THEN** that operation is blocked without alternate credential/target fallback, while retained Issues, accepted status and execution history remain available
