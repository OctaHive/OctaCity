# Как собрать Triage и Delivery через UI

Инструкция для обычного локального стенда OctaCity. Цель — два независимо
опубликованных pipeline: **Triage** записывает классификацию в Issue,
**Delivery** читает снимок данных Issue при запуске. Выбирать Run триажа
при запуске Delivery не требуется. Все настройки pipeline ниже выполняются
через UI, без подготовки Flow или Configuration через API.

Названия кнопок приведены преимущественно для английского интерфейса, чтобы
их можно было точно найти. Сведения о полях и размерах соответствуют
реализации с настраиваемым Project-каталогом Size.

## 1. Проверить стенд

На стенде должны быть актуальные **Server и Console**. Если нет раздела
**Sizes** или выбора порога спецификаций, сначала обновите сборки стенда:
повторный запуск старых образов новые элементы UI не добавляет.
Порядок обновления описан в [инструкции стенда](local-stand.md).

Используйте прежний root стенда и параметры установки. Исходный запуск:

```sh
tools/factory-stand \
  --github-token-file ./github.token \
  --delivery-write-directory tools \
  --delivery-target-branch main \
  --delivery-token-file ./github.token
```

Если Delivery должен создавать OpenSpec-файлы, установке нужны также
разрешённые каталоги для них. При обновлении повторите аргумент
`--delivery-write-directory` для каждого каталога, например `tools`,
`openspec/changes`, `openspec/specs`. Установка только с `tools` не разрешает
запись спецификаций вне этого каталога. Затем эти области надо явно подключить
к нужным шагам в UI.

В Project должны быть доступны:

- агент для анализа, агенты Coder, Tester, Reviewer и DevOps;
- локальное действие **Apply classification to Issue**;
- команды проверки baseline и кандидата, цель публикации draft PR;
- Access profiles **Triage**, **Delivery** и Launch policy **Standard**.

AI Profile выбранного агента и Access profile конфигурации — разные настройки.
Общий Access profile задаёт пределы pipeline; каждый шаг отдельно запрашивает
свои инструменты, документы и доступ к коду.

Готовый триаж, установленный стендом, можно оставить для сравнения. Далее
создаётся свой pipeline; новый пустой стенд для этого не нужен.

## 2. Подготовить поля Project

1. Откройте **Project → Issue field settings**.
2. Проверьте **Priorities**: исходные ID — `blocker`, `high`, `medium`, `low`.
   Это варианты поля Issue. Числа для планировщика задаются позже в Delivery.
3. В **Components** добавьте компоненты проекта. Для примера: имя `Console`,
   стабильный ID `console`. Список у каждого Project свой.
4. В **Issue types** оставьте или настройте `defect`, `feature_request`.
   Пример **Ticket delivery · v2** поддерживает именно эти два маршрута;
   новый тип требует отдельной настройки графа.
5. В **Sizes / Размеры** настройте варианты и их порядок **от меньшего к
   большему** кнопками **Up / Down**. Исходный порядок:
   `small → medium → large`. Можно добавить, например, `xl` после `large`.
   Имя можно менять, ID сохраняйте; старый вариант выводите из использования
   через **Retired**, а не заменяйте другим ID.
6. В **Custom Issue fields** создайте поля типа **Choice** и привяжите их к
   семантическим ролям классификации:

   | Поле                     | Пример ID вариантов                                                                          | Семантическая привязка      |
   | ------------------------ | -------------------------------------------------------------------------------------------- | --------------------------- |
   | Delivery risk            | `low`, `medium`, `high`, `critical`                                                          | **Risk field**              |
   | Delivery severity        | `low`, `medium`, `high`, `critical`                                                          | **Severity field**          |
   | Delivery route           | `development` для первого прогона                                                            | **Recommended route field** |
   | Delivery reproducibility | `reproduced`, `not_reproduced`, `unknown`, `needs_research`, `needs_input`, `not_applicable` | **Reproducibility field**   |

   Это отдельные свойства Issue с назначенной ролью. Одного совпадения имени
   поля с `risk` недостаточно: выберите его в соответствующей привязке.
   Дополнительные рекомендованные маршруты задавайте вместе с правилами их
   обработки; рекомендация сама по себе не меняет граф Delivery.

7. Нажмите **Review field definitions → Publish field definitions**.

Если другой оператор одновременно изменил каталог, обновите текущие данные
и выполните **Reconcile with current catalog**. Конфликт названия размера и
конфликт порядка согласуются отдельно: можно оставить своё название и текущий
порядок либо наоборот. Это работает и для размера со стабильным ID `order`.

Общие правила компонентов, приоритетов и оценки можно оформить в
**Project documents**. Документ объясняет значение вариантов, а каталог
задаёт допустимые ID. В триаже тип результата будет взят из этого каталога —
переписывать его вручную в каждом шаге не нужно.

## 3. Собрать Triage

Минимальный граф:

```text
assess — classified → apply — applied → завершение classified
```

### 3.1. Шаг assess: оценить Issue

1. Откройте **Factory → Add pipeline**, задайте **Pipeline name: Triage**.
2. Добавьте шаг `assess`, тип **Reasoning**.
3. В **Expected result** нажмите **Add result**. Назовите результат
   `classified` в технических деталях результата.
4. Выберите **Reuse Project classification fields**
   («Использовать поля классификации проекта»). Отметьте priority, component,
   type, size, risk, severity, recommended route и reproducibility, затем
   **Use selected field contracts**.
5. В **Result structure and limits** сделайте выбранные поля обязательными
   для этого минимального pipeline. Нажмите **Save result**. Используйте
   полученные имена полей: например, тип Issue в контракте классификации
   представлен как `kind`.
6. В **Executor** выберите совместимые Role/Profile, например
   **Systems analyst → Systems analysis**, и примените профиль через
   **Use profile**. Используйте доступную опубликованную версию.
7. Включите **Task from admitted Work**, чтобы агент получил исходную задачу.
   В **Documents** подключите точные публикации правил Project как reference
   material. Подключение документа к Project само по себе не передаёт его шагу.
8. В **Task instructions** задайте поручение, например:

   > Классифицируй исходную задачу по определениям и правилам выбранного Project.
   > Оцени priority, component, kind, size, risk, severity, recommended_route
   > и reproducibility. Возвращай стабильные ID допустимых вариантов из
   > выбранного контракта. Для feature_request воспроизводимость обычно
   > not_applicable. Для дефекта без проверки используй подходящий вариант
   > неопределённости; не заявляй verified reproduction по одному описанию.
   > Не изменяй внешнюю задачу. Применение результата выполняет следующий шаг.

Для первого прогона выберите ясную небольшую feature request. Если рабочий
триаж должен отклонять задачи вне целей, искать дубликаты или запрашивать
уточнения, добавьте отдельные проверки и их явные маршруты до применения
классификации. Один шаг `assess` выше проверяет базовый путь записи в Issue.

### 3.2. Шаг apply: записать классификацию

1. Добавьте шаг `apply`, тип **Server action**.
2. Соедините результат `assess.classified` со входом `apply`.
3. Включите **Apply classification to Issue**
   («Применять классификацию к задаче»).
4. Выберите те же поля Project и нажмите **Use Project classification**.
   Проверьте источник: принятый результат `assess`, outcome `classified`.
   Значения должны поступать из результата анализа.
5. В **Flow settings** задайте **Entry node: assess**. Добавьте завершение
   `classified`, выберите **Completion result: apply.applied**.
6. Соедините `apply.applied` с этим завершением. Сохраните или явно настройте
   требуемые редактором маршруты ошибок и остановки.

Именно `apply` записывает классификацию в Issue. Успешный результат аналитика
без этого действия остаётся оценкой, которую Delivery не обязан использовать.

### 3.3. Опубликовать Flow и Configuration

1. Заполните **Pipeline goals** и **Completion criteria**, сохраните их через
   review-диалоги. Пример цели: «Классифицировать Issue по правилам Project».
   Критерий: «Принятая классификация применена к связанному Issue либо
   причина отказа видна». Укажите `assess` получателем критериев.
2. Нажмите **Review required access**, проверьте запросы и **Apply to draft**.
3. Выполните **Validate draft → Review publication → Confirm publish**.
4. Откройте **Create configuration draft**, выберите опубликованный Triage.
5. Выберите **Launch policy: Standard**, **Access profile: Triage**.
6. Проверьте настройки, включите **Enabled**, провалидируйте и опубликуйте
   Configuration. Включение конфигурации не запускает Issue автоматически.

## 4. Проверить Triage на Issue

1. Создайте Issue с описанием, ожидаемым поведением и **Acceptance criteria**.
   Для первого прогона подойдёт маленькое изменение в разрешённом каталоге
   `tools` с проверяемым результатом.
2. Откройте Issue → **Start pipeline**, выберите Configuration Triage.
   Если форма требует репозиторий и ревизию, укажите проверяемый источник.
   Проверьте launch-параметры и подтвердите запуск.
3. Дождитесь завершения в **Runs**.
4. В Issue **Properties** проверьте значения priority, component, type, size
   и семантических полей. Проверьте происхождение классификации от pipeline
   и её актуальность. Карточка оценки и фактически применённые значения —
   разные результаты; для Delivery нужны применённые значения.

Вручную заполненный Issue тоже допустим. Triage — один из способов подготовки
данных, а не обязательный предшественник Delivery.

## 5. Собрать независимый Delivery

### 5.1. Открыть пример v2

1. В **Factory** выберите **Add pipeline → Start from an example →
   Ticket delivery · v2**.
2. Проверьте версию определений Project и список обязательных полей.
3. В **Snapshot admission** включите **Map Issue fields to admission**:

   - **Admission priority field**: Priority. Пример scheduling mapping:
     `blocker → 100`, `high → 80`, `medium → 50`, `low → 20`.
     Само поле priority остаётся выбором из вариантов Project.
   - **Admission risk field**: семантическое поле Delivery risk.
     Явно сопоставьте используемые значения с Low/Medium/High/Critical.
   - В allowed values разрешите `work_kind: feature_request` и/или `defect`.

   Незаполненная обязательная mapping блокирует запуск соответствующего Issue.

4. В **Create specifications starting at size**
   («Создавать спецификации начиная с размера») выберите порог.
   Например, при порядке `small → medium → large → xl` выбор `large`
   отправляет `large` и `xl` на подготовку спецификаций. Для меньших размеров
   используются явные критерии приёмки Issue.
5. Для reasoning-шагов выберите и примените совместимые установленные профили:

   | Назначение                                           | Обычный выбор на стенде                                       |
   | ---------------------------------------------------- | ------------------------------------------------------------- |
   | Реализация, подготовка спецификаций с записью файлов | Coder / Coder · Delivery с нужным доступом                    |
   | Подготовка защищённых тестов                         | Tester / Tester · Delivery, режим **Prepare protected tests** |
   | Независимая проверка                                 | Reviewer / Reviewer · Delivery                                |
   | Подготовка PR-метаданных                             | DevOps / DevOps · Delivery                                    |

   Заполните все обязательные executor-секции формы. Опциональному анализу CI,
   если он используется, нужен режим **Analyze CI results**.

6. Выберите совместимые команды baseline и обязательной проверки кандидата,
   затем установленную цель публикации PR. Reproduction-команда необязательна
   для feature request. Для дефекта без подтверждённого воспроизведения
   проверьте ветку reproduction или явной остановки/операторского решения.
7. Нажмите **Open example draft** и задайте имя, например `Delivery`.

Получится обычный редактируемый Flow. Порог уже скомпилирован в конкретные
правила gate `requirements_needed`. При изменении существующей политики
редактируйте этот gate и публикуйте новую версию Flow. Перестановка или
добавление размеров в Project не переписывает опубликованный маршрут.

Порог создания спецификаций и **человеческое согласование требований** —
отдельные правила. Проверьте gate согласования: пример содержит условия для
component `api`, size `medium`/`large`, priority `blocker`/`high`. Согласуйте их
с вариантами и правилами вашего Project, особенно при добавлении своих размеров.

### 5.2. Настроить код, задания и результат PR

1. В **Available code sources** добавьте репозиторий Project и проверяемую
   ревизию. Установите потолок доступа. Через **Code scope → Selected paths**
   ограничьте дерево нужными каталогами.
2. В каждом **Step code** явно выберите источник:

   - protected tests и baseline — исходная ревизия, read-only;
   - implementation — исходная ревизия, read/write в разрешённых каталогах;
   - specification author — нужные исходники и разрешённая область записи
     спецификаций;
   - review, protected validation, анализ сбоя и publisher — read-only,
     **Accepted candidate from another step → implementation → observed**.

   Добавление источника к Flow не подключает код всем шагам. Если Coder пишет
   в `/workspace/source`, это не выдаёт Tester право изменять тот же каталог.

3. В **Candidate capture → Require deliverables** согласуйте permitted paths
   и required kinds/paths с задачей на implementation и protected validation.
   Для изменения только в `tools` уберите несвязанные требования примера.
   Политики producer и validator должны совпадать.
4. В **Step task / Task instructions** задайте реальные поручения. Для
   protected tests — какие свойства независимо проверять; для implementation —
   что изменить и какие публичные регрессионные тесты оставить в кандидате.
   Агент работает в `/workspace/source`; `.git` может отсутствовать.
   Используйте установленные инструменты гостя: POSIX shell и Node. Наличие
   Python или `rg` на хосте не означает их наличие у агента.
5. Подключите документы и task-context только нужным шагам. Если необходимы
   комментарии или документы конкретного Issue, выполните раздел 7 ниже.
6. У шага `publish_pull_request` откройте результат `published`:
   **Edit result → Show on Issue → Pull request → Save result**.
   Так подтверждённая ссылка PR появится в Issue **Overview**.
7. Проверьте лимиты, инструкции и маршруты. Сохраните обязательные protected
   validation и независимый review перед публикацией PR.
8. Выполните **Review required access → Apply to draft**, затем
   **Validate draft → Review publication → Confirm publish**.

### 5.3. Опубликовать Configuration Delivery

1. Выберите **Create configuration draft**, точную опубликованную версию
   Delivery, **Launch policy: Standard**, **Access profile: Delivery**.
2. Проверьте настройки, включите **Enabled**, провалидируйте и опубликуйте.
3. Ни Flow триажа, ни его Run в этой конфигурации не выбираются.
   **Incoming pipeline completion** и `v1` нужны для отдельно выбранного
   сценария передачи точного результата между pipeline.

## 6. Запустить Delivery и проверить независимость

1. Вернитесь к подготовленному Issue. Проверьте актуальность классификации,
   обязательные поля и конкретные Acceptance criteria.
2. Выберите **Start pipeline → Configuration Delivery**, репозиторий и ревизию.
   **Use a result from an earlier run** для этого сценария не включайте.
3. На review проверьте снимок Issue, значения, происхождение и доступные
   материалы; подтвердите запуск. При конфликте сначала выполните новый review.
4. В **Runs** проверьте выбранную ветку, спецификации/согласования при
   необходимости, protected tests, реализацию, review, обязательную проверку
   и подтверждённую публикацию.
5. Проверьте draft PR и ссылку в Issue **Overview**.

Изменение Issue после запуска не меняет снимок уже принятого Run. Для нового
выполнения нужен новый запуск с новым review. Для проверки независимости можно
подготовить другой Issue вручную и запустить ту же Configuration Delivery:
запуск триажа для него не обязателен.

Preview запуска и детали снимка показывают название Size и его стабильный ID
из закреплённого каталога. Переименование размера в Project не подменяет это
название в сохранённом снимке. Если старая запись не содержит названия,
показывается ID без подстановки из текущего каталога.

## 7. Передать текст из Issue при необходимости

Пример Delivery v2 по умолчанию не читает весь текст комментариев и документов.
Если текст должен стать входом выполнения:

1. В Issue **Documents** создайте и опубликуйте документ задачи. Он остаётся
   Issue-owned и не появляется среди общих Project documents. Для общего
   документа используйте отдельное **Link existing Project document**.
2. В **Activity** напишите комментарий и отдельно включите нужный комментарий
   в Issue materials. Для документа тоже явно выберите конкретную публикацию.
3. До публикации потребляющего Flow откройте **Issue snapshot → Configure Issue
   snapshot**, включите **Include explicitly selected Issue materials**, задайте
   bounds и получателей в **Issue input for each step**. Сохраните через
   **Use Issue snapshot**, провалидируйте и опубликуйте новую версию.
4. Для запуска выберите Configuration, закреплённую на этой версии Flow,
   и проверьте точные материалы на review.

Публикация документа или комментария сама по себе не выбирает его как вход,
не запускает pipeline и не заменяет материал в уже принятом Run.

## 8. Если что-то не получается

| Симптом                                  | Что проверить                                                                                                                                |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| Нет Sizes или порога спецификаций        | Обновлены ли обе сборки — Server и Console                                                                                                   |
| Нет действия применения классификации    | Установлен ли локальный writer и его Project capability; запущен ли актуальный установщик с прежним root                                     |
| Нет полей risk/severity/reproducibility  | Опубликованы ли Choice-поля и выбраны ли семантические привязки                                                                              |
| Форма примера не открывает draft         | Все ли обязательные admission mappings, threshold, профили, команды и target выбраны; смотрите diagnostics                                   |
| Поля в Issue не изменились после анализа | Выполнился ли шаг apply и применена ли оценка без конфликта с ручными правками                                                               |
| Admission блокирует классификацию        | Обязательные значения, актуальность, evidence, mappings и allowed work_kind; текст «reproduced» сам по себе не является проверенным evidence |
| Не проходит запись кода/спецификаций     | Каталоги установки, Flow code scope, доступ конкретного шага и capture policy                                                                |
| Просят выбрать предыдущий Run            | Выбран ли snapshot-consumer v2, а не producer-result v1 или Incoming pipeline completion                                                     |
| Build упал                               | Run → Build/Job: events, результат и trace агента; проверяйте причину до повторного запуска                                                  |

Для первого ручного прогона оставьте автоматический Source intake и внешние
Reporter-эффекты выключенными. Их включение — отдельная настройка после
проверки двух опубликованных pipeline.

Подробности: [общий редактор Factory](factory-pipeline-authoring.md),
[контракт Delivery v2](../../config/factory/presets/ticket-delivery/README.md),
[проверки настраиваемого Size](../../openspec/changes/add-issue-classification-snapshots/verification-9.md).
